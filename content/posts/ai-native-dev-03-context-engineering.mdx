## 들어가며

에이전트에게 일을 시켜본 사람들은 비슷한 순간을 겪습니다.

"왜 이 코드는 이렇게 짜면 안 되는지"를 모델이 이해하지 못해서, 결과물이 미묘하게 우리 팀 컨벤션에서 벗어나는 순간입니다. 함수는 동작하지만 로그 형식이 다르고, 에러 처리 방식이 다른 파일과 어긋나고, 존재하지 않는 유틸리티를 새로 만들어 넣기도 합니다.

프롬프트를 아무리 정성껏 써도 매 요청마다 같은 규칙을 반복해서 알려주는 건 지속 가능하지 않습니다.

이때 필요한 개념이 context engineering입니다. 특히 에이전트가 리포지토리 자체를 "이해"하게 만드는 repository intelligence가 핵심입니다.

## repository intelligence란

repository intelligence는 에이전트가 단순히 파일 내용을 읽는 것을 넘어, 코드베이스의 구조와 규칙, 팀의 의도를 파악하게 만드는 것을 뜻합니다.

같은 코드를 봐도 신입 개발자와 시니어 개발자가 다르게 이해하는 것과 같습니다. 시니어는 함수 이름만 봐도 이 팀이 어떤 스타일을 선호하는지, 왜 이 레이어에서 트랜잭션을 열지 않는지, 어떤 모듈이 곧 사라질 예정인지를 안내받지 않아도 짐작합니다.

에이전트에게 이런 감각을 갖게 하려면 두 가지 방식이 있습니다. 하나는 정적으로 인덱싱된 RAG를 참조하게 하는 것이고, 다른 하나는 에이전트가 직접 코드베이스를 능동적으로 탐색하게 하는 것입니다.

## 정적 RAG와 능동적 탐색

몇 년 전에는 리포지토리 전체를 임베딩해서 벡터 DB에 넣고, 질문마다 top-k 청크를 붙여주는 방식이 유행이었습니다.

이 방식은 명확한 한계가 있습니다. 청크 경계에서 문맥이 잘리고, 파일 간의 관계는 임베딩 유사도로 드러나지 않고, 리팩토링이 있으면 인덱스가 금방 낡습니다. 무엇보다 "이 함수를 호출하는 곳은 어디인가"처럼 정확한 참조가 필요한 질문에는 취약합니다.

지금의 코딩 에이전트는 방향이 다릅니다. 필요한 파일을 grep하고, glob으로 탐색하고, 심볼을 따라가면서 스스로 컨텍스트를 넓혀갑니다. 사람이 IDE에서 하는 행동에 가깝습니다.

능동적 탐색이 강한 대신 비용이 있습니다. 에이전트가 "어디를 봐야 하는지" 감을 잡지 못하면 엉뚱한 폴더를 뒤지느라 시간과 토큰을 낭비합니다. 그래서 리포지토리 상단에 지도를 놓아둘 필요가 있습니다.

그 지도가 `CLAUDE.md`, `AGENTS.md` 같은 컨텍스트 파일입니다.

## CLAUDE.md가 하는 일

`CLAUDE.md`는 에이전트가 세션을 시작할 때 자동으로 읽는 지속적 지침입니다.

프롬프트에 매번 붙이지 않아도, 리포지토리에서 작업할 때는 항상 활성화되는 시스템 프롬프트에 가깝습니다. 여기에는 사람이 신입에게 온보딩 문서로 건네줄 만한 내용을 담습니다.

간단한 예시를 보겠습니다.

```markdown
# Project Context

이 리포지토리는 Node.js + TypeScript 기반의 결제 게이트웨이 서버입니다.

## 구조
- `src/api/` HTTP 진입점 (Fastify)
- `src/domain/` 순수 도메인 로직, 외부 의존 금지
- `src/infra/` DB, 외부 API 어댑터
- `src/jobs/` 배치와 큐 컨슈머

## 컨벤션
- 모든 외부 IO는 `src/infra/` 안에서만 발생합니다.
- 에러는 `AppError`를 상속받아 사용합니다. `throw new Error()` 금지.
- 로거는 `src/lib/logger.ts`의 pino 인스턴스만 사용합니다.
- 새 API는 반드시 zod 스키마 + OpenAPI 자동 생성이 필요합니다.

## 주의사항
- `payments` 테이블은 append-only입니다. UPDATE 대신 새 row를 넣으세요.
- `legacy/` 하위는 리팩토링 중이라 참고만 하고 수정하지 마세요.
```

핵심은 짧고 단정적으로 쓴다는 점입니다. 사람에게 설명하듯 문단으로 풀지 않고, 규칙과 위치를 명시합니다.

## A/B로 비교해 보기

컨텍스트 파일이 있을 때와 없을 때의 결과 차이는 생각보다 큽니다.

같은 프로젝트에서 "결제 재시도 API를 하나 추가해 줘"라는 프롬프트를 두 번 돌려봤습니다.

`CLAUDE.md`가 없는 상태에서 에이전트는 다음처럼 움직였습니다. 먼저 리포지토리 루트에서 파일 목록을 훑고, 이름이 유사한 파일을 몇 개 골라 읽어 봅니다. 컨트롤러를 어디에 둬야 할지 확신이 없어 `src/routes/` 아래에 만들었는데, 실제 컨벤션은 `src/api/`였습니다. 에러는 그냥 `throw new Error("retry failed")`로 처리했고, 새 로거를 `console.log`로 붙였습니다. 동작은 하지만 리뷰에서 다 지적당할 코드였습니다.

`CLAUDE.md`가 있는 상태에서는 같은 프롬프트에 대해 처음부터 `src/api/`에 컨트롤러를 만들고, `AppError`를 상속한 `PaymentRetryError`를 정의하고, 기존 pino 로거를 import 했습니다. 심지어 `payments` 테이블에 UPDATE를 치지 않고 새 row로 재시도 이력을 남기는 방향으로 스키마를 잡았습니다.

같은 모델, 같은 프롬프트, 다른 컨텍스트. 결과 품질이 리뷰 통과 여부를 가를 정도로 달라졌습니다.

## 대규모 코드베이스에서 방황을 줄이는 힌트

리포지토리가 커질수록 컨텍스트 파일 하나로는 부족해집니다.

이때 유용한 패턴이 몇 가지 있습니다.

첫째, 하위 디렉터리별 컨텍스트 파일을 둡니다. `src/domain/CLAUDE.md`에는 도메인 계층의 규칙만, `src/infra/CLAUDE.md`에는 DB 접근 패턴만 적습니다. 에이전트가 해당 디렉터리에서 작업할 때만 좁게 참조하도록 만들면 토큰을 아낄 수 있습니다.

둘째, "찾을 때 이 파일부터 봐라"는 힌트를 넣습니다.

```markdown
## 어디서 찾을까

- HTTP 라우팅: `src/api/routes.ts`가 진입점입니다.
- DB 스키마: `prisma/schema.prisma`가 정본, 마이그레이션은 `prisma/migrations/`
- 공통 타입: `src/types/` 하위, 도메인별 폴더로 분리
- 절대 건드리지 말 것: `src/legacy/`, `scripts/one-off/`
```

이 몇 줄이 있으면 에이전트가 파일 트리를 재귀적으로 훑는 시간을 크게 줄입니다.

셋째, 자주 하는 실수와 그 이유를 명시합니다.

```markdown
## 자주 하는 실수

- 트랜잭션은 서비스 레이어에서만 엽니다. 컨트롤러에서 열지 마세요.
- 외부 API 호출 앞에 반드시 timeout과 retry 설정이 필요합니다.
- `Date.now()` 직접 사용 금지. `src/lib/clock.ts`를 통해서만.
```

"금지"만 적지 말고 왜인지 한 줄 붙이면 에이전트가 유사 상황에서도 원칙을 적용합니다.

## 컨텍스트를 최소로 유지하기

역설적이지만 컨텍스트 파일은 짧을수록 좋습니다.

너무 많은 내용을 담으면 두 가지 문제가 생깁니다. 매 세션마다 토큰을 먹고, 정말 중요한 규칙이 덜 중요한 문장들 사이에 묻힙니다.

저는 다음 기준으로 다이어트를 합니다.

한 번만 어긋나도 리뷰에서 반드시 지적할 항목만 남깁니다. "이렇게 하면 좋다" 수준의 취향은 뺍니다. 코드에서 읽어낼 수 있는 내용은 굳이 문서로 옮기지 않습니다. 예를 들어 "TypeScript를 씁니다" 같은 문장은 `tsconfig.json`을 보면 되니 불필요합니다.

대신 코드만 봐서는 알기 어려운 이유와 맥락을 씁니다. "이 테이블이 왜 append-only인지", "왜 legacy 폴더를 건드리면 안 되는지" 같은 것들입니다.

## 마무리

프롬프트는 한 번의 대화를 다루지만 context engineering은 시스템의 지속적 배경을 만듭니다.

좋은 `CLAUDE.md`는 에이전트를 신입 개발자에서 팀의 사이드킥으로 승격시킵니다. 코드베이스의 지도, 컨벤션, 지뢰밭을 미리 알려주는 것만으로 결과물의 품질이 눈에 띄게 올라갑니다.

에이전트를 잘 쓰는 팀은 프롬프트 엔지니어링보다 컨텍스트 엔지니어링에 시간을 씁니다. 프롬프트는 사람이 매번 다르게 쓰지만, 컨텍스트는 리포지토리에 한 번 새겨두면 팀 전체가 혜택을 봅니다.
