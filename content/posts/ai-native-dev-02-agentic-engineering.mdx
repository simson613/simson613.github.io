## 들어가며

AI 네이티브 개발자 시리즈의 세 번째 글입니다. 앞선 글에서 마인드셋과 LLM 기초를 정리했고, 이번 글부터는 실제로 일하는 방식을 다룹니다.

이 자리에서 넘어야 할 언덕이 하나 있습니다. "vibe coding"에서 "agentic engineering"으로의 전환입니다.

두 표현이 비슷해 보이지만 내부 구조는 완전히 다릅니다. vibe coding은 순간의 감으로 프롬프트를 던지고 결과를 받는 자유로운 흐름이고, agentic engineering은 위임과 검증이 반복 가능한 시스템으로 굳어진 흐름입니다.

이 글은 그 전환을 개발자의 실무 관점에서 정리합니다.

## vibe coding이 나쁘지는 않다

먼저 오해를 풀고 시작하겠습니다. vibe coding 자체가 나쁘다는 이야기가 아닙니다.

새로운 라이브러리를 처음 만졌을 때, 문제의 형태가 아직 흐릿할 때, 브레인스토밍하듯 아이디어를 뽑고 싶을 때. 이런 국면에서는 자유로운 프롬프팅이 오히려 잘 맞습니다. 프롬프트 몇 개를 툭툭 던지면서 감을 잡는 시간은 필요하고, 그 시간을 아예 없애자는 얘기가 아닙니다.

문제는 이 방식으로 프로덕션 코드까지 끌고 가려고 할 때 생깁니다.

즉흥적 프롬프트로 짠 코드는 어떤 요구사항을 만족하려고 만든 건지 스스로도 명확히 설명하기 어렵습니다. 리뷰어에게 넘길 때 근거를 제시하기가 어렵고, 6개월 뒤에 왜 이렇게 짰는지 아무도 기억하지 못합니다. 테스트가 없는 경우도 많습니다.

혼자 프로토타입을 뽑을 때는 이 방식이 빠릅니다. 팀이 함께 유지보수하는 시스템으로 넘어가는 순간, 이 방식은 부채로 변합니다.

agentic engineering은 이 부채를 만들지 않기 위해 자유로움을 일부러 제한하는 방향입니다.

## agentic engineering의 정의

제가 쓰는 정의는 이렇습니다.

agentic engineering은 (1) 상위 목표를 (2) CLI 에이전트에 명확히 위임하고, (3) 에이전트가 계획-실행-검증 루프를 자율적으로 돌게 한 뒤, (4) 사람이 그 결과를 구조화된 방식으로 검증하고, (5) 이 흐름 자체를 팀 안에서 반복 가능하게 만드는 방식입니다.

핵심 단어는 "루프"와 "반복 가능성"입니다.

vibe coding은 매번 다르게 흘러갑니다. 오늘 잘 뽑힌 프롬프트가 내일 잘 뽑힌다는 보장이 없습니다. agentic engineering은 잘 굴러간 흐름을 슬래시 커맨드, 서브에이전트, 프로젝트 규칙으로 굳혀서 다음번에도 같은 품질을 재현할 수 있게 만듭니다.

이건 개인 취향의 문제가 아니라 팀 스포츠의 문제입니다.

## CLI 에이전트의 자율 실행 루프

CLI 에이전트가 다른 도구와 결정적으로 다른 지점은 자율 실행 루프에 있습니다.

챗봇 인터페이스에서는 사람이 질문을 하면 모델이 답합니다. 사람이 다음 질문을 하지 않으면 아무 일도 일어나지 않습니다. 흐름의 주도권이 사람에게 있습니다.

CLI 에이전트에서는 흐름이 다릅니다. 상위 목표 하나를 던지면 에이전트가 스스로 계획을 세우고, 파일을 읽고, 코드를 쓰고, 테스트를 돌리고, 실패하면 원인을 분석해서 다시 시도합니다. 사람은 이 루프의 시작과 끝에만 개입합니다.

대략 이런 구조입니다.

```text
사용자: "이 서비스에 idempotency-key 미들웨어를 붙이고 통합 테스트까지 추가해줘"

  ┌─────────────────────────────────────────────────┐
  │ 1. Plan                                          │
  │    - 관련 파일 탐색 (grep, glob)                  │
  │    - 기존 미들웨어 구조 파악                       │
  │    - 스토리지 선택, 검증 규칙, 실패 모드 정리        │
  ├─────────────────────────────────────────────────┤
  │ 2. Execute                                       │
  │    - 미들웨어 코드 작성 (Edit/Write)              │
  │    - 라우터에 연결                                │
  │    - 통합 테스트 작성                             │
  ├─────────────────────────────────────────────────┤
  │ 3. Verify                                        │
  │    - 타입 체크 / 린트 / 테스트 실행 (Bash)         │
  │    - 실패 시 원인 분석 후 2단계로 복귀             │
  ├─────────────────────────────────────────────────┤
  │ 4. Report                                        │
  │    - 변경 파일 요약, diff, 미검증 항목             │
  └─────────────────────────────────────────────────┘

사용자: (결과 검증, 필요 시 재위임)
```

이 루프의 자율성이 실질적인 차이를 만듭니다. 사람이 매 스텝마다 확인 버튼을 누르지 않아도 되기 때문에 처리량이 늘고, 사람은 상위 판단과 최종 검증에 시간을 쓸 수 있습니다.

물론 자율성이 위험이기도 합니다. 잘못된 방향으로 자율적으로 달려가면 사람이 뒷수습할 코드가 산더미가 됩니다. 그래서 위임의 판단이 중요해집니다.

## 위임할 것 vs 직접 할 것

저는 요즘 태스크를 받으면 잠깐 멈춰서 두 축으로 평가합니다.

첫 번째 축은 "검증하기 쉬운가"입니다. 결과가 맞는지 빠르게 확인할 수 있으면 위임 후보입니다. 유닛 테스트로 확인되는 순수 함수, 스키마가 명확한 데이터 변환, 반복적 CRUD 코드가 여기 속합니다. 반대로 결과의 정합성을 사람이 눈으로 오래 봐야만 알 수 있는 태스크는 위임이 잘 안 됩니다.

두 번째 축은 "실패 시 위험이 낮은가"입니다. 잘못 나와도 되돌리기 쉬운 태스크는 위임 부담이 적습니다. 실패 시 시스템 전체가 흔들리거나, 되돌리기 어려운 마이그레이션이 필요한 태스크는 사람이 손을 대야 합니다.

이 두 축을 매트릭스로 그려보면 대략 이렇게 됩니다.

- 검증 쉬움 + 위험 낮음: 무조건 위임합니다. 여기서 얻은 시간이 상위 판단에 재투자됩니다.
- 검증 쉬움 + 위험 높음: 위임하되 사람이 반드시 리뷰합니다. 자동 테스트만 믿지 않습니다.
- 검증 어려움 + 위험 낮음: 위임할 수 있지만 결과를 소비하는 방식을 조심합니다. 참고 자료로만 쓰고 그대로 머지하지 않는 편이 안전합니다.
- 검증 어려움 + 위험 높음: 위임하지 않습니다. 아키텍처 결정, 도메인 모델링, 트레이드오프 판단 같은 것들이 여기에 들어갑니다.

이 프레임이 만병통치는 아니지만, 매번 감으로 결정하는 것보다는 훨씬 낫습니다. 특히 팀에 이 기준을 공유해두면 위임 실패로 인한 뒷수습이 크게 줄어듭니다.

## 에이전트가 실제로 도구를 다루는 방식

CLI 에이전트가 개발자처럼 일할 수 있는 건 실제 개발 도구에 손을 댈 수 있기 때문입니다.

셸을 통해 명령을 실행하고, 파일 시스템을 읽고 쓰고, 테스트를 돌리고, git 상태를 확인합니다. 어떤 에이전트는 브라우저를 열어 문서를 확인하고, 어떤 에이전트는 스크린샷을 찍어 UI를 검증하기도 합니다.

이 도구 접근성이 붙는 순간 에이전트의 결과 품질이 크게 달라집니다. 코드를 짜기만 하는 챗봇과, 자기가 짠 코드가 정말 돌아가는지 실행해보고 실패하면 고치는 에이전트는 완전히 다른 종족입니다.

실무에서 저는 프로젝트 루트에 `CLAUDE.md` 같은 프로젝트 규칙 파일을 두고 에이전트에게 컨벤션과 금기를 미리 알려둡니다. 대략 이런 톤입니다.

```markdown
# 이 리포지토리에서 지킬 것들

## 언어와 스타일
- TypeScript strict 모드. any 금지.
- 서비스 코드는 함수형 스타일 우선, 클래스는 도메인 엔티티에만.

## 테스트
- 변경 코드는 반드시 대응 테스트가 있어야 함.
- 통합 테스트는 `tests/integration/` 하위에 둔다.
- 테스트 없이 PR 올리지 말 것.

## 커밋
- Conventional Commits 규격 사용.
- 하나의 커밋은 하나의 의도만 담는다.

## 금지 사항
- `console.log` 남기지 말 것. 로깅은 `logger`를 통해서.
- 프로덕션 DB 스키마를 직접 수정하는 스크립트를 만들지 말 것.
- 외부 API 키를 코드에 하드코딩하지 말 것.
```

이 파일 하나만 잘 유지해도 에이전트의 결과가 팀 컨벤션에 훨씬 잘 맞아 들어옵니다. 사람 신입에게 온보딩 문서를 주는 것과 성격이 비슷합니다.

## 장기 실행 태스크와 사이클

vibe coding에서는 태스크가 대개 짧습니다. 프롬프트 하나에 30초짜리 응답 하나입니다.

agentic engineering에서는 태스크의 시간 단위가 훨씬 깁니다. 저는 하루 중에 몇 번, 30분에서 몇 시간짜리 태스크를 에이전트에 통째로 맡겨두고 다른 일을 합니다. 예를 들어 "이 모듈 전체를 새 아키텍처로 마이그레이션하고 테스트까지 통과시켜줘" 같은 태스크는 사람이 붙어 있을 필요가 없습니다.

이때 중요한 건 태스크를 던지기 전 스펙과 성공 기준을 명확히 잡는 것입니다. "테스트가 다 초록이면 성공", "이 파일들의 diff가 이런 형태여야 함", "이 벤치마크 수치가 이 이하여야 함" 같은 식입니다.

성공 기준이 없는 채로 장기 태스크를 던지면 에이전트는 그럴듯한 뭔가를 열심히 만들어 옵니다. 그런데 검증할 기준이 없어서 사람이 결과를 다시 뜯어봐야 합니다. 이러면 위임의 이점이 대부분 사라집니다.

에이전트가 결과를 반환하면 저는 다음 세 가지를 순서대로 봅니다.

1. 성공 기준이 정말 충족됐는가 (테스트, 벤치마크, 스펙 항목)
2. diff가 원했던 범위 안에 들어와 있는가 (스코프 크립이 없는가)
3. 코드베이스의 일관성이 유지되고 있는가 (이름 규칙, 레이어링, 로깅 스타일)

이 세 가지 중 하나라도 어긋나면 그 사이클은 실패로 기록하고 다시 위임합니다. 대충 넘기는 순간부터 부채가 쌓입니다.

## 실패 사례를 패턴화한다

위임했다가 실패한 사례를 매번 다르게 겪으면 배움이 축적되지 않습니다.

저는 실패한 위임 사례를 짧게 기록해둡니다. 어떤 태스크였고, 어떤 프롬프트로 위임했고, 결과가 왜 안 맞았는지, 다시 하면 뭘 바꿔야 하는지를 두세 줄로 남깁니다.

이 기록이 쌓이면 패턴이 보입니다. 예를 들어 저의 경우 이런 패턴들이 반복적으로 드러났습니다.

첫째, 도메인 모델을 새로 설계해야 하는 태스크에서 위임이 자주 실패했습니다. 에이전트가 표면적 구조는 그럴듯하게 뽑는데, 우리 도메인의 진짜 제약을 반영하지 못했습니다. 이런 태스크는 지금은 사람이 먼저 스켈레톤을 잡고 그 안을 채우는 방식으로만 위임합니다.

둘째, 라이브러리 최신 API가 관련된 태스크에서 잘 틀렸습니다. 에이전트가 예전 API를 기억해서 그 시그니처로 코드를 짜는 경우가 많았습니다. 이런 경우 공식 문서 링크나 원문을 컨텍스트에 같이 넣어주면 실패율이 크게 낮아졌습니다.

셋째, 성능이 결과 기준인 태스크는 검증이 어려웠습니다. 벤치마크를 미리 세팅해두지 않으면 사후 검증이 안 됩니다.

이 패턴들을 알고 나면 다음번 위임에서 미리 방어할 수 있습니다. "이런 종류의 태스크는 위임 전에 스켈레톤이나 문서를 붙이자", "이런 태스크는 벤치마크부터 먼저 만들자" 같은 규칙이 자연스럽게 생깁니다.

## 마무리

vibe coding에서 agentic engineering으로의 전환은 도구를 바꾸는 게 아니라 일하는 흐름의 구조를 바꾸는 일입니다.

자유로움 자체는 여전히 유용하지만, 그 자유로움 위에 위임 기준, 성공 조건, 검증 절차, 실패 기록 같은 뼈대를 얹어야 팀이 함께 유지할 수 있는 시스템이 됩니다.

이 시리즈의 다음 글에서는 이 뼈대의 앞자리에 놓이는 스펙 주도 개발을 다루려고 합니다. 위임 전에 스펙을 어떻게 잡을 것인가, 무엇을 결정하고 무엇을 열어둘 것인가에 대한 이야기입니다.
