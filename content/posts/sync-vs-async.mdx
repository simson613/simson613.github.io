## 들어가며

백엔드 서버가 하는 일의 상당 부분은 무언가를 기다리는 것입니다.

DB 응답을 기다리고, 외부 API 호출을 기다리고, 디스크 읽기를 기다립니다. 정작 CPU가 계산하는 시간은 그 사이 잠깐입니다. 그래서 "기다리는 시간을 어떻게 다루느냐"가 서버의 처리량을 좌우합니다. 동기와 비동기는 바로 이 기다림을 다루는 두 가지 방식입니다.

## 동기/비동기와 블로킹/논블로킹은 다른 축이다

먼저 자주 뒤섞여 쓰이는 네 단어를 정리하고 갑니다.

- 동기(sync) / 비동기(async): 호출한 쪽이 결과를 어떻게 받느냐입니다. 동기는 호출한 자리에서 결과가 나올 때까지 챙기고, 비동기는 "끝나면 알려줘"라고 맡겨두고 나중에 통보(콜백, 이벤트, future)를 받습니다.
- 블로킹(blocking) / 논블로킹(non-blocking): 호출이 제어권을 언제 돌려주느냐입니다. 블로킹은 작업이 끝날 때까지 제어권을 안 돌려주고, 논블로킹은 일단 바로 돌려줍니다.

실무에서 가장 자주 만나는 조합은 두 가지입니다. "동기 + 블로킹"(결과 나올 때까지 스레드가 멈춰 대기)과 "비동기 + 논블로킹"(맡겨두고 다른 일 하다가 통보받기)입니다.

## 동기 블로킹 - 스레드 하나가 요청 하나

전통적인 서버 모델은 요청 하나에 스레드 하나를 붙입니다.

```java
// 요청을 처리하는 스레드가 DB 응답이 올 때까지 멈춰 있다
User user = db.query("SELECT * FROM users WHERE id = ?", id);  // blocking
Order order = api.fetchOrder(user.orderId());                  // blocking
return render(user, order);
```

이 방식은 코드가 위에서 아래로 읽히기 때문에 직관적이고 디버깅이 쉽습니다. 문제는 DB나 외부 API가 응답하는 동안 그 스레드가 아무 일도 못 하고 놀고 있다는 점입니다.

동시에 처리할 수 있는 요청 수가 곧 스레드 풀 크기가 됩니다. 그런데 스레드는 공짜가 아닙니다. 각자 스택 메모리(보통 수백 KB에서 1MB)를 잡고, 수가 많아지면 컨텍스트 스위치 비용도 커집니다. 커넥션 만 개를 동시에 감당하려고 스레드 만 개를 띄우는 건 현실적이지 않습니다.

## 비동기 논블로킹 - 이벤트 루프

비동기는 이 문제를 다르게 풉니다.

I/O 요청을 보낸 뒤 그 자리에서 기다리지 않고, "완료되면 이 작업을 이어서 해줘"라고 등록한 다음 다른 일을 처리합니다. I/O가 끝나면 이벤트 루프가 등록해둔 작업을 깨워 이어서 실행합니다.

```javascript
// 이벤트 루프 위에서: await 지점에서 스레드를 놓아준다
async function handler(id) {
  const user = await db.query("SELECT * FROM users WHERE id = ?", id);
  const order = await api.fetchOrder(user.orderId);
  return render(user, order);
}
```

코드 모양은 동기와 비슷해 보이지만, `await` 지점에서 이 요청은 스레드를 붙잡지 않고 놓아줍니다. 그 사이 같은 스레드가 다른 요청 수백 개를 처리합니다. 그래서 Node.js, Nginx, Netty 같은 서버는 스레드 몇 개로 수천, 수만 커넥션을 감당합니다.

## 비동기는 무엇을 빠르게 하는가

여기서 오해하기 쉬운 지점이 있습니다.

비동기는 CPU 계산 자체를 빠르게 만드는 게 아닙니다. I/O를 기다리는 동안 스레드가 놀지 않게 만들어 처리량을 끌어올리는 것입니다. 그래서 비동기는 I/O 바운드 작업에서 크게 이깁니다. 반대로 CPU 바운드 작업에서는 이득이 거의 없습니다.

오히려 위험할 수 있습니다. 이벤트 루프 위에서 무거운 계산이나 동기 블로킹 호출을 하면, 그 순간 루프 전체가 멈추고 그 스레드에 매달린 모든 요청이 함께 멈춥니다. 그래서 비동기 서버에서 무거운 작업은 별도 워커 스레드나 프로세스로 오프로드해야 합니다.

## 언제 무엇을 쓰나

- I/O가 대부분이고 동시 커넥션이 많다면(API 게이트웨이, 프록시, 실시간 서버) 비동기가 유리합니다.
- CPU 바운드거나, 트래픽이 크지 않아 단순함이 더 중요하다면 동기 블로킹으로도 충분합니다. 무리해서 비동기로 짜면 코드만 복잡해집니다.
- 언어가 Go처럼 런타임에서 비동기를 감춰준다면, 동기 스타일로 쓰면서 처리량을 함께 얻을 수 있습니다.

## 마무리

동기는 직관적이지만 기다리는 동안 자원을 놀립니다. 비동기는 처리량을 얻는 대신 복잡성을 짊어집니다.

결국 이 선택은 "많은 요청을 스레드를 늘려서 감당할 것인가, 이벤트 루프로 감당할 것인가"의 문제입니다. 그리고 그 판단의 출발점은 언제나 "이 서버가 CPU를 갈고 있는가, 무언가를 기다리고 있는가"를 정확히 아는 것입니다.
