## 들어가며

AI 기능을 붙인 서비스를 운영해 본 사람은 압니다.

시연할 때는 잘 되던 기능이 배포하고 며칠 지나면 이상해지고, 프롬프트를 살짝 바꿨더니 다른 케이스가 깨지고, 모델 버전이 올라갔더니 톤이 미묘하게 달라지는 일이 반복됩니다. "잘 된다"의 기준이 사람 감각에 있으면 이 문제를 절대 못 잡습니다.

그래서 백엔드 채용에서 실제로 검증하는 능력도 그 사이 옮겨갔습니다.

"AI를 쓸 줄 안다"는 이제 시그널이 아닙니다. AI를 안 쓰는 개발자를 찾기가 더 어렵기 때문입니다. 반면 "AI 시스템의 올바른 출력을 정의하고, 회귀를 자동으로 잡아내는 하네스를 만들 줄 안다"는 아직도 희소합니다.

이 글은 그 하네스 이야기입니다.

## 올바른 출력을 정의하는 능력

eval의 출발점은 "올바른 출력이 무엇인가"를 정의하는 일입니다.

이게 생각보다 어렵습니다. 결정론적인 코드라면 입력과 출력이 딱 정해집니다. `sum(1, 2)`는 `3`이고 그 외는 버그입니다. 그런데 LLM은 다릅니다. "고객 문의를 분류해서 담당 팀으로 라우팅하라"는 태스크에서 "결제팀"이 정답인지 "결제/CS팀"이 정답인지 애매합니다.

이때 개발자가 해야 하는 일은 애매함을 걷어내고 판정 가능한 기준을 만드는 것입니다. 그 기준을 만드는 과정 자체가 도메인 이해와 요구사항 정의의 결합이라 대체가 어렵습니다.

기준을 만드는 방식은 대개 세 가지입니다.

- **정확 일치**: 라벨, JSON 필드, 특정 값 같은 구조화된 출력에 씁니다.
- **규칙 기반**: "고객 이름이 반드시 포함되어야 한다", "500자 이하여야 한다", "특정 금칙어가 없어야 한다" 같은 검사.
- **의미 기반**: 임베딩 유사도, LLM-as-judge. 자유 서술에 씁니다.

가능하면 위쪽부터 씁니다. 정확 일치로 처리할 수 있는 걸 굳이 LLM으로 판정하지 않습니다.

## 골든셋 만들기

기준이 잡혔으면 그 기준을 적용할 대상, 즉 골든셋이 필요합니다.

골든셋은 실제 사용자 요청을 대표할 수 있는 입력-정답 쌍의 집합입니다. 초기에는 실서비스 로그에서 다양한 케이스를 뽑아 팀원이 라벨링하는 방식이 가장 실용적입니다.

이때 신경 써야 하는 건 커버리지입니다.

- 흔한 케이스(happy path)
- 애매한 경계 케이스
- 실패해도 되는 케이스와 절대 실패하면 안 되는 케이스
- 최근 프로덕션에서 실제로 깨졌던 케이스

특히 마지막이 중요합니다. 사고가 났을 때 그 케이스를 골든셋에 추가하는 습관을 들이면 골든셋은 자연스럽게 자산이 됩니다. 회귀 테스트 스위트가 시간이 지나면서 두꺼워지는 것과 같은 원리입니다.

한 번에 완벽한 골든셋을 만들려 하지 말고, 50개 정도로 시작해서 계속 채워 나가는 게 현실적입니다.

## eval 하네스 구조

하네스의 뼈대는 단순합니다.

골든셋을 순회하며 시스템을 실행하고, 결과를 채점하고, 리포트를 냅니다. pytest 스타일로 간단히 짜면 이런 모양이 됩니다.

```python
import json
import pytest
from myapp.agent import route_ticket

with open("evals/tickets_golden.jsonl") as f:
    CASES = [json.loads(line) for line in f]

@pytest.mark.parametrize("case", CASES, ids=lambda c: c["id"])
def test_ticket_routing(case):
    result = route_ticket(case["input"])
    assert result["team"] == case["expected_team"], (
        f"[{case['id']}] expected={case['expected_team']} got={result['team']}"
    )
    assert result["confidence"] >= 0.5
```

이렇게 짜두면 CI에서 그대로 돌릴 수 있고, 실패한 케이스가 어떤 것이었는지 즉시 드러납니다.

자유 서술처럼 정확 일치가 어려운 태스크는 규칙 판정과 LLM-as-judge를 혼합합니다.

```python
def test_summary_quality(case):
    summary = summarize(case["input"])
    assert 100 <= len(summary) <= 400
    assert not contains_banned_terms(summary)
    score = llm_judge(
        rubric=SUMMARY_RUBRIC,
        input=case["input"],
        output=summary,
        reference=case["reference"],
    )
    assert score >= 4  # 1~5 스케일
```

핵심은 하네스가 코드로 존재하고, 실행 가능하고, 재현 가능해야 한다는 점입니다. 노션에 정리한 표는 하네스가 아닙니다.

## LLM-as-judge의 활용과 한계

자유 서술을 채점할 때 LLM-as-judge는 편리한 도구입니다.

프롬프트 하나로 사람 라벨링을 부분적으로 대체할 수 있고, 대량 케이스를 짧은 시간에 채점할 수 있습니다. 다만 그 한계를 이해하고 써야 합니다.

우선 judge 프롬프트 예시를 봅니다.

```text
당신은 요약문 채점자입니다. 아래 원문과 요약을 보고
다음 rubric에 따라 1~5점을 매기고 이유를 한 줄로 설명하세요.

Rubric:
5 - 원문의 핵심 사실을 모두 담고 사실 왜곡이 없음
4 - 핵심은 담았으나 사소한 누락이 있음
3 - 절반 이상의 정보를 담았으나 중요한 사실이 빠짐
2 - 사실 왜곡이 하나 이상 있음
1 - 완전히 다른 내용이거나 사용 불가

원문:
{input}

요약:
{output}

응답 형식: {"score": <int>, "reason": "<string>"}
```

이 방식의 한계는 명확합니다.

첫째, judge도 모델이므로 편향과 실수를 합니다. 특히 길이가 길거나 확신에 찬 어투에 더 높은 점수를 주는 경향이 있습니다.

둘째, judge의 정확도 자체를 검증해야 합니다. 사람 라벨 100건 정도에 대해 judge 점수와 사람 점수의 일치율을 봐야 신뢰할 수 있는 지표가 됩니다.

셋째, judge 프롬프트가 바뀌면 과거 점수와 비교가 안 됩니다. rubric은 코드처럼 버전 관리해야 합니다.

실무 팁 하나 덧붙이면, judge 모델은 시스템 모델과 다른 벤더나 다른 버전을 씁니다. 같은 모델로 자기 출력을 채점하면 편향이 더 커집니다.

팁을 하나 더. 위 프롬프트는 응답 형식을 자연어로 부탁하고 있지만, 실제로는 구조화 출력(structured output)으로 형식을 강제하는 편이 안전합니다. JSON 스키마나 tool 호출로 `{score, reason}` 형태(점수는 1에서 5 사이 정수)를 못 박아 두면, judge가 가끔 형식을 어겨 파싱이 깨지거나 점수 범위를 벗어나는 일을 생성 단계에서 막을 수 있습니다. 채점 파이프라인은 대량으로 자동 실행되기 때문에, 이 작은 형식 안정성이 지표 자체의 신뢰도를 좌우합니다.

## CI에 붙이기

eval의 진짜 가치는 회귀를 자동으로 잡는 데 있습니다.

프롬프트를 바꾸든, 모델을 올리든, 리트리버를 손보든 어딘가는 반드시 나빠집니다. 사람 감각으로는 절대 못 잡습니다. CI에 eval을 붙여 두면 이걸 자동으로 잡습니다.

GitHub Actions 워크플로우는 이런 정도면 시작으로 충분합니다.

```yaml
name: eval

on:
  pull_request:
    paths:
      - "prompts/**"
      - "src/agent/**"
      - "evals/**"

jobs:
  run-eval:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
      - run: pip install -e ".[eval]"
      - name: Run eval suite
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
        run: pytest evals/ --junitxml=eval-report.xml
      - uses: actions/upload-artifact@v4
        if: always()
        with:
          name: eval-report
          path: eval-report.xml
```

여기서 조금 더 나가면 baseline과 비교해서 "몇 점 이상 떨어지면 실패" 같은 임계값을 두게 됩니다. 특정 태그가 붙은 케이스는 절대 깨지면 안 되는 회귀 케이스로 표시해 두는 것도 좋습니다.

프롬프트 변경 PR에서 eval 스코어 diff가 자동으로 코멘트로 붙는 순간, 팀의 AI 기능 안정성이 한 단계 올라갑니다.

## 신뢰 격차와 채용 시그널

여기서 요즘 채용 시장의 신뢰 격차 이야기를 하고 싶습니다.

"AI를 쓴다"고 말하는 개발자는 이제 흔합니다. 그런데 "AI를 검증하고, 제약하고, 평가한다"고 말하는 개발자는 여전히 드뭅니다. 채용 인터뷰에서 이 차이를 확인하는 방식이 점점 정교해지고 있습니다.

전형적인 질문은 이런 식입니다.

- 지금 서비스 중인 LLM 기능이 있다면 골든셋은 몇 개이고 어떻게 만들었는가.
- 프롬프트를 바꿨을 때 회귀가 없다는 걸 어떻게 확인하는가.
- LLM-as-judge를 쓴다면 judge 자체의 정확도는 어떻게 검증했는가.
- 프로덕션에서 잘못된 출력이 나왔을 때 그 케이스가 다음 배포에서 다시 나오지 않는다는 걸 어떻게 보장하는가.

여기에 구체적으로 대답할 수 있는 사람과 그렇지 않은 사람의 격차가 지금 채용 시그널의 핵심입니다.

백엔드 개발자에게 이 스킬이 특히 유리한 이유는 배경이 정확히 맞기 때문입니다. 테스트 하네스를 짜본 경험, CI에 붙여본 경험, SLI/SLO를 설계해 본 경험, 회귀를 잡아본 경험이 그대로 eval에 이식됩니다. 프론트나 데이터 사이언스 쪽에서 이 파이프라인을 처음부터 짜는 것보다 훨씬 빠릅니다.

## 코드 리뷰가 아니라 출력 리뷰

관점 하나를 바꿔야 합니다.

전통적인 코드 리뷰는 "이 코드가 어떤 동작을 하는가"를 봅니다. AI가 코드를 쓰기 시작하면서 리뷰의 초점이 "이 코드가 어떤 출력을 만드는가"로 옮겨갑니다.

AI가 생성한 코드는 문법적으로 그럴듯하지만 논리 오류나 환각을 자주 담습니다. 존재하지 않는 API를 부르고, 실제와 다른 스키마를 가정하고, 미묘하게 잘못된 정규식을 씁니다. 사람 리뷰만으로는 놓치기 쉬운 종류의 오류입니다.

여기서 eval 하네스가 다시 등장합니다. 코드 자체를 리뷰하는 대신 그 코드가 만드는 출력을 골든셋으로 리뷰하는 겁니다. 사람의 눈은 몇 개 케이스만 훑고, 나머지는 하네스가 잡습니다.

리뷰 루틴을 이렇게 잡습니다.

- AI 생성 코드가 들어오면 그 코드가 커버해야 할 케이스를 골든셋에 추가한다.
- 하네스가 통과하는지 먼저 본다.
- 그 후 사람은 로직의 접근 방식과 엣지 케이스 처리만 확인한다.

이 순서가 바뀌면 사람이 문법을 리뷰하다 실제 논리 오류를 놓칩니다.

## 마무리

AI 시스템에서 진짜 어려운 일은 좋은 프롬프트를 쓰는 게 아닙니다.

좋은 프롬프트는 몇 번 시도하면 만들 수 있습니다. 어려운 건 그 프롬프트가 앞으로도 좋다는 걸 계속 증명하는 일이고, 나빠졌을 때 즉시 알아채는 일이고, 나빠진 이유를 특정할 수 있는 일입니다.

그 일을 하는 도구가 eval입니다.

골든셋을 만들고, 하네스를 짜고, LLM-as-judge를 신중하게 다루고, CI에 붙여 회귀를 잡는 이 흐름이 앞으로 AI 기능을 다루는 백엔드 개발자의 기본 소양이 됩니다.

무엇이 옳은 출력인가를 정의하고 그 정의를 코드로 강제할 수 있는 사람, 지금 그 사람이 가장 귀합니다.
