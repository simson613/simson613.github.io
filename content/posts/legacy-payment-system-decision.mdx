# 레거시 결제 시스템을 리팩토링할 것인가, 재작성할 것인가

2025년 초, 팀에 하나의 과제가 떨어졌다. 5년된 결제 시스템의 개선. 장애가 분기마다 한 번씩 터지고 있었고, 새로운 결제 수단 추가에 평균 3주가 걸리고 있었다.

선택지는 두 가지였다.

## 선택지 1: 점진적 리팩토링

기존 코드를 살리면서 조금씩 개선하는 방법.

**장점:**
- 서비스 중단 없이 진행 가능
- 기존 비즈니스 로직 보존
- 리스크가 상대적으로 낮음

**단점:**
- 근본적인 구조 문제 해결이 어려움
- 레거시 코드와의 타협이 계속됨
- 완료 시점이 불명확

## 선택지 2: 완전 재작성

새로운 아키텍처로 처음부터 다시 만드는 방법.

**장점:**
- 깨끗한 설계로 시작
- 현재 요구사항에 최적화 가능
- 기술 부채 청산

**단점:**
- 개발 기간이 길다 (최소 3개월)
- 기존 시스템과의 병행 운영 필요
- "두 번째 시스템 증후군" 위험

## 내가 내린 결론: 점진적 리팩토링

결론부터 말하면, **점진적 리팩토링**을 선택했다. 이유는 세 가지였다.

### 1. 결제는 돈이 오가는 시스템이다

결제 시스템의 특수성을 간과하면 안 된다. 재작성 중에 발생하는 버그 하나가 실제 금전적 손실로 이어진다. 5년간 쌓인 엣지 케이스 처리 로직을 새 시스템에서 100% 재현한다는 보장이 없었다.

```typescript
// 이런 코드가 곳곳에 있었다
// "왜 이렇게 했지?" 싶지만 실제 장애 대응에서 나온 로직들
if (pgResponse.code === 'V102' && retryCount < 3) {
  await delay(retryCount * 1000)
  return retry(request)
}
```

이 한 줄의 `V102` 처리가 왜 있는지 아는 사람이 팀에 아무도 없었다. 하지만 이걸 빼면 특정 PG사에서 간헐적 결제 실패가 발생한다는 걸 나중에야 알게 됐다.

### 2. 팀 상황

당시 결제 도메인을 이해하는 개발자가 나 포함 2명이었다. 재작성은 최소 4명이 3개월 이상 매달려야 하는 프로젝트였고, 다른 프로젝트 일정을 고려하면 현실적이지 않았다.

### 3. Strangler Fig 패턴이라는 대안

완전 재작성의 장점(깨끗한 설계)을 리팩토링에서도 얻을 수 있는 방법이 있었다. [Strangler Fig 패턴](https://martinfowler.com/bliki/StranglerFigApplication.html)을 적용해서, 새로운 기능은 새 아키텍처로 만들고 기존 기능은 점진적으로 마이그레이션하는 전략을 택했다.

```
┌─────────────────────────────────┐
│          API Gateway            │
│  ┌──────────┐ ┌──────────────┐  │
│  │ Legacy   │ │ New Payment  │  │
│  │ Payment  │ │ Service      │  │
│  │ Module   │ │ (신규 결제)    │  │
│  └──────────┘ └──────────────┘  │
└─────────────────────────────────┘
         ↓ 점진적 마이그레이션 ↓
┌─────────────────────────────────┐
│          API Gateway            │
│  ┌──────────────────────────┐   │
│  │ New Payment Service      │   │
│  │ (전체 결제)               │   │
│  └──────────────────────────┘   │
└─────────────────────────────────┘
```

## 6개월 후 회고

결과적으로 이 선택은 **절반만 맞았다**.

**잘한 점:**
- 서비스 장애 없이 마이그레이션 진행
- 새로운 결제 수단 추가 시간이 3주 → 5일로 단축
- 팀원들이 점진적으로 새 아키텍처를 학습

**아쉬운 점:**
- 레거시와 신규 시스템 병행 기간이 예상(3개월)보다 훨씬 길어짐 (6개월+)
- 두 시스템 사이의 데이터 정합성 관리에 예상 외의 공수 투입
- "점진적"이라는 말에 속아 구체적인 마일스톤 없이 진행한 기간이 있었음

## 배운 것

> 의사결정에서 가장 중요한 건 "어떤 선택을 했느냐"가 아니라 "그 선택의 리스크를 얼마나 관리했느냐"다.

리팩토링을 선택한 것 자체는 합리적이었지만, **마일스톤 없는 점진적 개선은 영원히 끝나지 않는다**는 교훈을 얻었다. 다음에 같은 상황이 온다면 "점진적 리팩토링 + 명확한 마일스톤 + 데드라인"을 세트로 가져갈 것이다.
