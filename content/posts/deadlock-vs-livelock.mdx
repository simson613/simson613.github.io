## 들어가며

여러 스레드가 자원을 공유하면 락이 필요하고, 락을 쓰기 시작하면 새로운 종류의 문제가 따라옵니다.

서버가 어느 순간 응답을 멈추고 아무것도 진행되지 않거나, CPU는 100%인데 정작 일은 하나도 끝나지 않는 현상. 이 둘의 원인이 각각 데드락과 라이브락입니다. 이름은 비슷하지만 증상과 대응이 다릅니다. 하나는 완전히 멈춘 것이고, 다른 하나는 멈추지 못해서 문제입니다.

## 데드락이란

데드락은 둘 이상의 실행 흐름이 서로가 쥔 자원을 기다리며 영원히 멈춘 상태입니다.

가장 흔한 예가 계좌 이체입니다. 스레드 하나는 A 계좌를 잠그고 B를 잠그려 하고, 다른 하나는 B를 잠그고 A를 잠그려 합니다. 둘 다 상대가 쥔 락을 기다리므로 아무도 앞으로 못 갑니다.

```java
// 스레드 1: transfer(A, B)
synchronized (A) {
    synchronized (B) { ... }   // B는 스레드 2가 쥐고 있음 → 대기
}

// 스레드 2: transfer(B, A)
synchronized (B) {
    synchronized (A) { ... }   // A는 스레드 1이 쥐고 있음 → 대기
}
```

두 스레드가 정확히 반대 순서로 락을 잡는 순간, 서로를 붙잡고 영원히 기다립니다.

## 데드락의 네 가지 필요조건

데드락은 다음 네 조건이 **동시에** 성립할 때만 발생합니다. Coffman 조건이라고 부릅니다.

1. 상호 배제(mutual exclusion): 자원을 한 번에 하나의 흐름만 쥘 수 있다.
2. 점유와 대기(hold and wait): 자원을 쥔 채로 다른 자원을 기다린다.
3. 비선점(no preemption): 남이 쥔 자원을 강제로 뺏을 수 없다.
4. 순환 대기(circular wait): 대기 관계가 고리를 이룬다(A는 B를, B는 A를 기다림).

중요한 건 네 개가 전부 필요하다는 점입니다. 그래서 이 중 하나만 깨뜨리면 데드락을 예방할 수 있습니다.

## 데드락 예방과 회피

실무에서 쓰는 방법들은 대부분 위 네 조건 중 하나를 겨냥합니다.

가장 실용적인 건 **락 순서를 고정하는 것**입니다. 순환 대기를 없애는 방법입니다. 계좌 이체라면 항상 계좌 id가 작은 쪽부터 잠급니다. 그러면 모든 스레드가 같은 순서로 락을 잡으니 고리가 생기지 않습니다.

```java
// 락 순서를 id로 고정 → 순환 대기 제거
Account first  = a.id < b.id ? a : b;
Account second = a.id < b.id ? b : a;
synchronized (first) {
    synchronized (second) { ... }
}
```

그 밖의 방법도 각각 조건 하나를 깹니다.

- **타임아웃 + 재시도**: `tryLock`으로 일정 시간 안에 못 잡으면 쥔 락을 모두 놓고 처음부터 다시 시도합니다. 비선점 조건을 완화합니다.
- **필요한 락을 한 번에 획득**: 작업 시작 전에 필요한 락을 모두 확보하고, 하나라도 실패하면 전부 놓습니다. 점유와 대기를 없앱니다.
- **공유 자체를 없애기**: 불변 데이터, 단일 스레드 모델(Redis), 메시지 패싱을 쓰면 락이 필요 없어 데드락도 없습니다.
- **탐지 후 회복**: 예방 대신 탐지하는 접근입니다. DB는 대기 그래프(wait-for graph)에서 고리를 찾으면 한쪽 트랜잭션을 희생자로 골라 롤백합니다.

## 라이브락이란

라이브락은 상태는 계속 바뀌는데 진도가 나가지 않는 상태입니다.

데드락은 완전히 멈추지만, 라이브락은 부지런히 움직입니다. 다만 그 움직임이 서로를 상쇄해서 아무것도 완료되지 않습니다. 좁은 복도에서 마주친 두 사람이 서로 비켜주려다 계속 같은 방향으로 움직여 부딪히는 상황과 같습니다. 둘 다 열심히 양보하는데 지나가지를 못합니다.

코드로는 이런 모양입니다.

```text
스레드 1: 락 A 잡음 → 락 B 시도 실패 → "양보하자" → A 놓고 재시도
스레드 2: 락 B 잡음 → 락 A 시도 실패 → "양보하자" → B 놓고 재시도
→ 둘이 동시에 놓고 동시에 다시 잡기를 무한 반복
```

데드락을 피하려고 "실패하면 양보"를 넣었는데, 두 스레드가 완벽히 같은 타이밍으로 양보하면서 오히려 라이브락에 빠지는 겁니다. CPU는 계속 바쁘지만 결과물은 없습니다.

## 데드락과 라이브락, 그리고 기아

| 구분 | 데드락 | 라이브락 |
|------|--------|----------|
| 상태 | 완전히 멈춤 | 계속 변하지만 진전 없음 |
| CPU | 대기 상태(놀고 있음) | 바쁨(헛돌고 있음) |
| 겉보기 | 응답 없음, 프로세스 정지 | 살아 있는데 처리량 0 |

여기에 기아(starvation)도 함께 알아둘 만합니다. 특정 스레드가 자원을 계속 얻지 못해 영원히 밀리는 상태입니다. 우선순위가 낮거나 불공정한 락에서 생깁니다. 라이브락은 여러 스레드가 서로 양보하다 다 같이 못 가는 것이고, 기아는 그중 특정 스레드만 계속 뒤로 밀리는 것으로 볼 수 있습니다.

## 백엔드에서 실제로 만나는 곳

애플리케이션 코드보다 **DB 트랜잭션**에서 데드락을 훨씬 자주 만납니다.

한 트랜잭션이 로우 X를 잠그고 Y를 잠그려는데, 다른 트랜잭션이 Y를 잠그고 X를 기다리면 데드락입니다. 대부분의 DB는 이걸 탐지해서 한쪽을 자동으로 롤백하고 에러를 던집니다. 그래서 실무 대응은 세 가지로 정리됩니다.

- 여러 로우를 갱신할 때 항상 같은 순서로 접근합니다(예: 기본 키 오름차순).
- 트랜잭션을 짧게 유지하고, 락을 오래 쥐지 않도록 인덱스를 잘 걸어 스캔 범위를 좁힙니다.
- 데드락으로 롤백당할 수 있다고 가정하고, 재시도 로직을 기본으로 깔아 둡니다.

라이브락은 재시도 로직 자체에서 튀어나오기 쉽습니다. 실패하자마자 모두가 즉시, 같은 간격으로 재시도하면 계속 같은 자리에서 충돌합니다. 그래서 재시도에는 **랜덤 지터를 섞은 지수 백오프**를 씁니다. 각자 조금씩 다른 시점에 다시 시도하게 만들어 충돌 확률을 떨어뜨리는 것입니다.

## 마무리

데드락은 멈춘 것이고, 라이브락은 멈추지 못하는 것입니다.

데드락은 락 순서를 고정하거나 탐지 후 롤백으로 다루고, 라이브락은 양보 로직을 다듬고 백오프에 무작위성을 넣어 다룹니다. 둘 다 결국은 공유 상태와 락에서 비롯됩니다.

그래서 가장 근본적인 해법은 애초에 공유와 락을 줄이는 쪽입니다. 불변 데이터, 메시지 패싱, 단일 스레드 모델이 꾸준히 주목받는 이유가 여기에 있습니다. 락을 정교하게 다루는 기술도 중요하지만, 락을 쓸 필요가 없는 구조가 언제나 더 강합니다.
