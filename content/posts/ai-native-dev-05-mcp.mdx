## 들어가며

에이전트가 유용해지는 순간은 외부 세계에 손을 댈 수 있게 되는 지점입니다.

DB를 조회하고, 사내 API를 호출하고, 파일 시스템을 읽고, 사내 위키를 뒤지는 일까지 대신할 수 있어야 진짜 일이 됩니다. 문제는 이런 연동을 벤더마다 다른 방식으로 만들어두면 도구가 늘어날수록 유지보수 지옥이 온다는 점입니다.

MCP는 이 문제를 해결하려고 나온 표준입니다.

작년까지만 해도 각 제공사가 자기 방식대로 tool calling을 정의했지만, 지금은 Anthropic이 만든 이 프로토콜이 사실상 업계 표준이 되었습니다. 주요 모델 제공사와 IDE 대부분이 클라이언트로 지원하는 상태입니다.

백엔드 개발자 입장에서 이 표준을 이해하고 있으면 얻는 게 큽니다. 우리가 이미 만들어 둔 시스템을 그대로 노출해 에이전트가 쓰게 할 수 있고, 반대로 남이 만든 도구를 우리 에이전트에 붙일 수 있습니다.

## MCP가 표준이 된 배경

MCP는 원래 Anthropic 내부에서 Claude가 외부 도구를 다루기 위해 만든 프로토콜이었습니다.

공개되자마자 반응이 컸던 이유는 문제 정의가 정확했기 때문입니다. 모델이 도구를 호출하는 방식은 벤더마다 조금씩 달랐고, 도구 하나를 만들면 GPT용, Claude용, Gemini용을 따로 관리해야 했습니다. IDE나 에이전트 프레임워크마다 플러그인 규격도 제각각이었습니다.

MCP는 이 계층을 하나로 통일했습니다. 서버는 표준 스펙에 맞게 도구를 노출하고, 클라이언트는 표준 스펙에 맞게 호출합니다. 중간 모델이 무엇이든 상관하지 않는 구조입니다.

지금은 OpenAI, Google, Anthropic을 비롯한 주요 제공사와 IDE(Cursor, VS Code, JetBrains) 대부분이 MCP 클라이언트를 지원합니다. 자체 방식을 병행하는 곳도 있지만, 공통 분모로는 MCP가 확실히 자리잡았습니다.

표준이 자리 잡았다는 건 우리가 만든 서버 하나로 여러 클라이언트를 커버할 수 있다는 뜻입니다.

## 프로토콜 구조

MCP는 크게 두 가지 전송 방식을 지원합니다.

첫 번째는 stdio입니다. 클라이언트가 자식 프로세스로 서버를 띄우고 표준 입출력으로 JSON-RPC 메시지를 주고받는 방식입니다. 로컬에서 IDE 확장처럼 쓰기에 적합하고, 인증이 사실상 프로세스 소유자로 끝나기 때문에 설정이 단순합니다.

두 번째는 Streamable HTTP입니다. 원격 서버를 붙일 때 쓰는 방식이고, 실무에서 우리 서비스를 노출할 때 대부분 이 방식을 씁니다. 초기에는 HTTP + SSE(POST 엔드포인트와 별도 SSE 스트림을 두는 방식)를 썼지만, 단일 엔드포인트 기반의 Streamable HTTP로 대체되면서 기존 SSE 방식은 deprecated 됐습니다. 인증은 OAuth 2.1이 표준 권장이지만, 사내용이면 API key나 mTLS도 흔히 씁니다.

프로토콜이 정의하는 핵심 primitive는 세 개입니다.

- `tools`: 에이전트가 호출할 수 있는 함수. `list_orders`, `create_ticket` 같은 것들.
- `resources`: 에이전트가 읽을 수 있는 데이터. 파일, DB row, 문서 등.
- `prompts`: 재사용 가능한 프롬프트 템플릿.

실무에서 90퍼센트는 tools만 잘 정의하면 됩니다.

## 기존 MCP 서버 붙여 보기

이해가 빠른 방법은 이미 있는 서버를 하나 붙여 보는 겁니다.

Cursor나 Claude Desktop을 쓴다면 설정 파일에 다음처럼 등록합니다.

```json
{
  "mcpServers": {
    "filesystem": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "/Users/me/work"]
    },
    "postgres": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-postgres",
               "postgresql://readonly:pw@localhost/mydb"]
    }
  }
}
```

이 상태에서 에이전트에게 "어제 주문 중 실패한 건 몇 개인가"라고 물어보면, Postgres MCP 서버를 통해 실제 DB 쿼리를 돌리고 결과를 요약합니다.

여기서 이미 두 가지 감이 옵니다. 첫째, 노출된 서버는 에이전트가 마음대로 쓸 수 있으므로 권한 경계가 매우 중요합니다. 위 예에서 굳이 `readonly` 유저로 붙인 이유입니다. 둘째, 도구 이름과 설명이 나쁘면 에이전트가 엉뚱한 도구를 호출합니다.

## 커스텀 MCP 서버 만들기

우리 서비스를 노출하고 싶다면 직접 서버를 만드는 게 실용적입니다.

Node에서 공식 SDK를 쓰면 매우 짧게 끝납니다.

```ts
import { McpServer } from "@modelcontextprotocol/sdk/server/mcp.js";
import { StdioServerTransport } from "@modelcontextprotocol/sdk/server/stdio.js";
import { z } from "zod";

const server = new McpServer({ name: "orders", version: "0.1.0" });

server.tool(
  "get_order",
  "주문 ID로 단건 주문을 조회합니다. 상태, 금액, 상품 목록을 반환합니다.",
  { orderId: z.string().describe("주문 ID, 형식: ORD-xxxxxxxx") },
  async ({ orderId }) => {
    const order = await db.orders.findUnique({ where: { id: orderId } });
    if (!order) return { content: [{ type: "text", text: "not found" }] };
    return { content: [{ type: "text", text: JSON.stringify(order) }] };
  },
);

await server.connect(new StdioServerTransport());
```

Go 진영도 공식 SDK가 있고 구조는 비슷합니다. 핸들러를 등록하고 stdio나 HTTP transport에 연결하는 패턴입니다.

이 서버 하나만 있으면 Claude, Cursor, VS Code, 사내 에이전트 어디서든 같은 도구를 씁니다. 언어와 프레임워크에 관계없이 우리 코드를 그대로 재사용할 수 있다는 게 MCP의 진짜 가치입니다.

## 인증과 보안 경계

여기서부터가 백엔드 개발자의 몫입니다.

MCP 서버는 결국 우리 시스템에 뚫린 새 창구입니다. 에이전트가 실수하거나 프롬프트 인젝션에 넘어가면 도구가 위험한 방향으로 호출될 수 있습니다.

실무에서 반드시 두는 방어선이 몇 가지 있습니다.

첫째, DB를 노출할 때는 반드시 read-only 유저와 별도 스키마로 격리합니다. 필요한 테이블만 view로 감싸서 노출하고, 개인정보 컬럼은 view에서 제외합니다.

둘째, 파괴적 작업은 별도 확인 단계를 둡니다. `delete_user` 같은 도구는 아예 노출하지 않거나, dry-run 모드로만 노출하고 실제 실행은 사람이 트리거하게 합니다.

셋째, 원격 HTTP 서버는 OAuth 2.1 + scope로 권한을 좁힙니다. 도구별로 필요한 scope를 명시하고, 사용자 세션에 맞춰 발급된 토큰으로만 호출되도록 강제합니다.

넷째, 감사 로그를 남깁니다. 어떤 세션의 어떤 요청이 어떤 도구를 어떤 인자로 호출했는지 전부 남겨야 문제가 생겼을 때 추적이 됩니다.

MCP 자체가 인증을 강제하는 게 아니라 서버 개발자가 층을 쌓아야 하는 구조라는 점을 잊으면 안 됩니다.

## 좋은 tool description 쓰는 법

에이전트가 도구를 잘 쓰느냐는 대부분 description에서 갈립니다.

나쁜 예를 먼저 봅니다.

```ts
server.tool("query", "쿼리를 실행합니다.", { sql: z.string() }, ...);
```

이런 도구는 에이전트가 언제 써야 하는지, 어떤 형식이 맞는지, 어떤 위험이 있는지 아무 정보가 없습니다. 결과적으로 아무 쿼리나 던지거나 아예 안 씁니다.

같은 도구를 이렇게 쓰면 훨씬 낫습니다.

```ts
server.tool(
  "run_analytics_query",
  `분석용 read-only 쿼리를 실행합니다.
   - orders, users, products 세 테이블만 접근 가능합니다.
   - SELECT 문만 허용되며 결과는 최대 1000 rows로 잘립니다.
   - 데이터 수정, 스키마 변경, 개인정보 조회 목적으로는 사용하지 마세요.
   - 사용 전에 사용자에게 어떤 쿼리를 실행할지 요약해서 알려주세요.`,
  { sql: z.string().describe("실행할 SELECT 쿼리. 세미콜론 없이 단일 문장.") },
  ...,
);
```

무엇을 하는 도구인지, 언제 쓰면 안 되는지, 인자 형식은 어떤지, 사용자와 어떻게 상호작용해야 하는지가 모두 담깁니다.

description은 사람이 아니라 모델이 읽는 문서라고 생각하고 쓰는 게 좋습니다. 모호한 표현은 환각을 낳고, 구체적인 제약은 오용을 줄입니다.

특히 조심할 부분은 이름입니다. `get_data`, `run_query`, `do_it` 같은 이름은 에이전트가 여러 도구 사이에서 헷갈리게 만듭니다. 이름만 봐도 무엇을 하는지 명확한 동사와 목적어 조합이 필요합니다.

## 마무리

MCP는 화려한 기술이 아니라 접착제입니다.

에이전트와 우리 시스템 사이를 잇는 표준이고, 이 표준이 잡히면서 개별 벤더에 종속되지 않고 우리 도구를 만들 수 있게 되었습니다.

백엔드 개발자에게 MCP는 특히 반가운 존재입니다. 우리가 이미 갖고 있는 것들, DB, 사내 API, 배치 스크립트, 어드민 기능이 곧바로 에이전트가 쓸 수 있는 도구가 됩니다. 새로운 걸 만드는 게 아니라 기존 걸 잘 노출하는 문제로 바뀝니다.

다만 노출하는 순간 보안 경계와 도구 설계 품질이 우리의 책임이 됩니다. 좋은 tool description을 쓰는 감각, 파괴적 작업을 안전하게 다루는 감각, 감사 로그를 남기는 감각이 앞으로 백엔드 개발자의 기본 소양이 될 겁니다.

에이전트가 안전하고 유용하게 우리 시스템을 다루게 하는 일, 그 인터페이스를 설계하는 사람은 결국 서버를 아는 사람입니다.
