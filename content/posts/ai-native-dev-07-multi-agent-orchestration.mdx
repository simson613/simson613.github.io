## 들어가며

에이전트 하나로 처리하는 코딩 태스크가 익숙해질 즈음, 자연스럽게 다음 질문이 따라옵니다.

"이걸 여러 개 동시에 돌리면 더 빠르지 않을까?"

실제로 스키마 설계, API 구현, 테스트 작성, 문서 정리 같은 작업은 어느 정도 독립적으로 나눌 수 있습니다. 각 작업에 특화된 에이전트를 붙이고, 오케스트레이터가 이들을 조율한 뒤 결과를 통합하면 순차 처리보다 훨씬 빠르게 끝날 것 같습니다.

먼저 김을 빼두겠습니다. 결론은 "되도록 하나로 하라"에 가깝습니다. 지난 1~2년 사이 현장에서 반복해 확인된 건, 컨텍스트 윈도우가 길어진 지금은 대부분의 코딩 태스크에서 단일 에이전트가 긴 컨텍스트를 들고 순차로 처리하는 쪽이 더 빠르고 안정적이라는 사실입니다. 멀티 에이전트는 조율·통합·실패 처리라는 고정 비용을 얹기 때문에, 그 비용을 상쇄할 만큼 태스크가 느슨하게 분해될 때만 이깁니다. 그래서 이 글은 "멀티 에이전트를 어떻게 만드나"보다 "언제 멀티로 가고 언제 가지 말아야 하나, 갈 거면 무엇을 설계해야 하나"에 대한 이야기에 가깝습니다.

문제는 이 아이디어가 정확히 백엔드 개발자가 오래 씨름해 온 주제라는 점입니다. 여러 서비스가 병렬로 일하고, 중간에 실패하고, 서로 다른 결정을 내리고, 그 결과를 합쳐야 하는 문제. 이름만 마이크로서비스가 아니라 멀티 에이전트일 뿐입니다.

이 글에서는 멀티 에이전트 오케스트레이션을 분산 시스템의 관점으로 다시 보고, 자율성 레벨과 핸드오프 프로토콜을 어떻게 설계할지 정리해봅니다.

## 오케스트레이터와 서브 에이전트

멀티 에이전트 아키텍처의 기본 구조는 단순합니다.

```text
                ┌────────────────────┐
                │   Orchestrator     │
                │  (planner, judge)  │
                └─────────┬──────────┘
                          │
        ┌─────────────────┼─────────────────┐
        │                 │                 │
┌───────▼────────┐ ┌──────▼───────┐ ┌───────▼────────┐
│ Schema Agent   │ │  API Agent   │ │  Test Agent    │
│ (DB, 마이그레) │ │ (핸들러, DTO)│ │ (unit, e2e)    │
└────────────────┘ └──────────────┘ └────────────────┘
```

오케스트레이터가 전체 태스크를 쪼개고, 각 서브 에이전트에게 할당하고, 결과를 받아 통합합니다.

이 구조가 실제로 익숙한 이유는 백엔드에서 늘 하던 것이기 때문입니다. API 게이트웨이가 여러 서비스에 fan-out 하고, 각 서비스가 자기 도메인의 응답을 만들고, 게이트웨이가 응답을 합쳐서 클라이언트에게 돌려주는 흐름과 다르지 않습니다.

## 순차 처리와 병렬 처리의 트레이드오프

에이전트를 하나만 쓰고 순차로 처리하면 단순합니다. 컨텍스트가 하나로 이어지고, 작업 순서가 명확하고, 디버깅이 쉽습니다.

반면 멀티 에이전트로 병렬 처리하면 속도가 빨라지지만 다른 문제가 생깁니다.

첫째, 컨텍스트 분산 문제입니다. 각 에이전트는 자기 작업에 필요한 컨텍스트만 봅니다. Schema Agent가 정의한 컬럼 이름을 API Agent가 정확히 알아야 하는데, 이걸 어떻게 전달할지가 문제입니다.

둘째, 결과 통합 문제입니다. Schema Agent가 `user_id` 라고 정의했는데 API Agent가 `userId` 로 받으면 실제 코드에서 어긋납니다. 백엔드에서 마이크로서비스 간 계약을 맞추기 위해 protobuf나 OpenAPI를 쓰는 것과 같은 이유로, 에이전트 간에도 공유 스키마가 필요합니다. 요즘은 이 계약을 생성 시점에 강제하는 수단이 하나 더 있습니다. 구조화 출력(structured output)입니다. 에이전트가 결과를 자유 텍스트로 뱉게 두지 않고 JSON 스키마나 tool 호출 형식으로 내도록 강제하면, `user_id`/`userId` 같은 어긋남의 상당수를 생성 단계에서 막을 수 있습니다.

셋째, 실패 처리 문제입니다. Schema Agent는 성공했는데 API Agent가 실패했을 때, 이걸 롤백할지 재시도할지 결정해야 합니다. 분산 트랜잭션과 사가 패턴이 다시 등장합니다.

즉 멀티 에이전트가 빨라 보이는 것은 어디까지나 조율 비용이 무시할 만할 때의 얘기입니다. 태스크가 서로 강하게 얽혀 있으면 순차 에이전트가 오히려 나을 수 있습니다.

## 자율성 레벨 프레임워크

에이전트에게 얼마만큼의 재량을 줄지에 대한 프레임워크로 자율성 레벨을 정의해두면 얘기가 편해집니다.

| 레벨 | 이름 | 사람의 개입 | 예시 |
|------|------|-------------|------|
| L1 | 어시스트 | 모든 결정 사람이 | 코드 자동완성, 인라인 제안 |
| L2 | 감독 실행 | 계획 승인 후 실행 | 스펙 주면 코드 작성, PR 리뷰 |
| L3 | 조건부 자율 | 저위험은 자동, 고위험은 승인 | 테스트/린트는 자동 수정, 스키마 변경은 확인 |
| L4 | 고자율 | 사람은 예외만 대응 | 이슈 감지, 수정, 배포까지 자동 |
| L5 | 완전 자율 | 사람 개입 없음 | 이론적 이상, 프로덕션엔 아직 없음 |

2026년 현재 대부분의 프로덕션 환경은 L2와 L3 사이에 있습니다. 코드 작성과 리뷰까지는 에이전트가 하되, 실제 머지와 배포는 사람이 확인합니다.

이 레벨을 명시적으로 정하지 않으면 팀 안에서 기대치가 어긋납니다. 어떤 사람은 "왜 에이전트가 알아서 배포 안 하지" 라고 하고, 다른 사람은 "왜 에이전트가 마음대로 코드를 밀어붙이지" 라고 합니다.

## 핸드오프 프로토콜

에이전트 사이의 통신은 사람이 읽을 수 있는 자연어보다 스키마화된 메시지가 낫습니다. 그리고 이 메시지는 다음 에이전트가 자유 텍스트에서 짐작해 채우는 게 아니라, 구조화 출력으로 형식을 강제해 주고받는 것이 안전합니다.

```json
{
  "task_id": "task-2026-07-06-001",
  "from_agent": "schema-agent",
  "to_agent": "api-agent",
  "status": "completed",
  "artifact": {
    "type": "schema",
    "path": "db/migrations/20260706_add_users.sql",
    "summary": "users 테이블 추가 (id, email, created_at)"
  },
  "contract": {
    "table": "users",
    "columns": [
      { "name": "id", "type": "bigint", "nullable": false },
      { "name": "email", "type": "varchar(255)", "nullable": false },
      { "name": "created_at", "type": "timestamp", "nullable": false }
    ]
  },
  "next_action": "generate_crud_api"
}
```

이 메시지가 있으면 다음 에이전트는 무엇이 완료되었고, 무엇을 근거로 다음 작업을 시작해야 하는지 명확합니다.

핸드오프 프로토콜이 있으면 얻는 것은 두 가지입니다. 하나는 에이전트 간 계약이 코드로 검증 가능해진다는 것이고, 다른 하나는 사람이 중간에 개입해 확인하기 쉬워진다는 것입니다.

## 충돌 해결과 상태 보고

여러 에이전트가 같은 파일을 건드리면 반드시 충돌이 납니다.

Schema Agent가 `users` 테이블을 만들고, API Agent가 `users` 라우트를 추가하고, Test Agent가 `users` 관련 픽스처를 만드는 동안, 서로 다른 파일을 편집한다는 보장은 없습니다. `types.ts` 하나에 여러 에이전트가 동시에 쓰기를 시도할 수 있습니다.

해결책도 우리가 이미 아는 것들입니다. 다만 파일 단위 락부터 떠올리기 쉬운데, 요즘 코딩 에이전트에서 더 잘 통하는 방식은 버전 관리 시스템 자체를 격리 수단으로 쓰는 것입니다.

가장 실용적인 방식은 각 에이전트를 독립된 git 브랜치(또는 worktree)에서 작업시키고, 오케스트레이터가 완료된 산출물을 원자적으로 병합하는 것입니다. 같은 작업 트리를 놓고 실시간으로 락을 잡는 대신, 각자 격리된 사본에서 일하고 병합 시점에만 충돌을 해소합니다. 병합 중 충돌이 나면 오케스트레이터가 해당 파일을 한 에이전트에게 몰아주거나 사람에게 올립니다. 여러 개발자가 한 리포지토리를 동시에 만지는 문제를 git이 이미 풀어둔 방식 그대로입니다. 파일 단위 락은 git으로 격리하기 어려운 공유 리소스(같은 DB 스키마, 외부 상태)에만 남겨두면 됩니다.

상태 보고는 주기적인 하트비트와 이벤트 스트림으로 처리합니다. 각 에이전트가 진행 상태, 완료 예상 시간, 발견한 이슈를 오케스트레이터에게 밀어 넣고, 오케스트레이터는 이를 모아 사람에게 요약해 보여줍니다.

## 역할 분담형 워크플로우 예시

간단한 CRUD API 하나를 멀티 에이전트로 만들어 본다고 해봅시다.

```text
1. Planner Agent
   - "users 리소스에 대한 CRUD API를 만들어라" 를 세부 태스크로 쪼갠다.
   - Schema, API, Test Agent에게 각각 태스크를 할당한다.

2. Schema Agent (병렬 시작)
   - 마이그레이션 파일 작성
   - contract 메시지 발행

3. API Agent (Schema 완료 이벤트 대기 → 시작)
   - 핸들러, DTO, 라우팅 작성
   - contract 메시지 발행

4. Test Agent (Schema 완료 이벤트 대기 → 시작)
   - 픽스처 준비
   - API contract 도착 시 e2e 테스트 작성

5. Judge Agent
   - 모든 산출물을 모아 리뷰
   - 실패 조건이 있으면 관련 에이전트에게 재작업 요청
```

여기서 중요한 것은 Test Agent와 API Agent가 부분적으로 병렬로 진행된다는 점입니다. Test Agent가 픽스처와 뼈대 테스트를 미리 준비하고, API contract가 나오는 순간 실제 검증 로직을 채우면 전체 시간이 줄어듭니다.

## 여러 모델을 같은 태스크에 돌리기

멀티 에이전트의 또 다른 활용은 같은 작업을 서로 다른 모델에 병렬로 시켜 결과를 비교하는 것입니다.

로직이 복잡한 리팩터링, 성능 최적화, 애매한 스펙 해석 같은 케이스에서 유용합니다. 각 모델의 답을 나란히 놓고 Judge Agent가 테스트 통과 여부, 코드 스타일, 변경 범위를 기준으로 하나를 고르거나, 사람이 최종 결정을 합니다.

이 방식은 비용이 들지만, 중요한 결정에서는 값어치를 합니다. 백엔드에서 여러 캐시 계층을 두거나 여러 DB replica를 두고 tail latency를 낮추는 것과 발상이 같습니다. 잉여를 만들어 신뢰도를 산다는 관점입니다.

## 분산 시스템으로서의 멀티 에이전트

정리해보면 멀티 에이전트 오케스트레이션은 결국 분산 서비스 조율 문제입니다.

각 에이전트는 하나의 마이크로서비스이고, 오케스트레이터는 API 게이트웨이 겸 사가 코디네이터이고, 핸드오프 메시지는 서비스 간 계약이고, 자율성 레벨은 서비스 권한 등급입니다.

백엔드 개발자가 이 영역에서 강점을 가지는 이유가 여기 있습니다. 우리는 이미 이런 시스템을 여러 번 만들어 봤습니다. 이제는 노드가 결정론적 코드가 아니라 확률적 에이전트라는 점이 달라졌을 뿐입니다.

## 마무리

멀티 에이전트가 빠르다는 말은 반만 맞습니다. 조율 비용을 감당할 수 있을 만큼 태스크가 잘 분해될 때만 빠릅니다.

실제로 우리가 설계해야 하는 것은 에이전트 자체보다 오케스트레이터입니다. 어떤 태스크를 병렬로 나눌지, 언제 핸드오프하고 언제 병합할지, 실패했을 때 무엇을 롤백할지. 이 결정이 시스템의 실질적인 성능을 결정합니다.

자율성 레벨을 명시적으로 정하고, 핸드오프 메시지를 스키마로 강제하고, 충돌 지점을 미리 식별해두면 멀티 에이전트는 위험한 실험이 아니라 관리 가능한 아키텍처가 됩니다.
