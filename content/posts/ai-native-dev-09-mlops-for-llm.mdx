## 들어가며

LLM 기반 기능을 실서비스에 올려본 분들은 처음 부딪히는 벽이 비슷할 겁니다.

로컬에서는 잘 되던 프롬프트가 트래픽이 조금만 붙으면 지연이 튀고, 월말 API 청구서를 보면 예상보다 두세 배가 나옵니다. 며칠 지나면 같은 프롬프트인데 응답 품질이 미묘하게 바뀌고, 사용자 문의는 늘어나는데 어디서부터 손대야 할지 애매합니다.

개발자 관점에서 보면 이건 결국 우리가 이미 해오던 문제입니다. 컨테이너로 배포하고, 캐시로 비용을 줄이고, 지표로 품질을 감시하는 파이프라인입니다. 다만 대상이 결정적 코드가 아니라 확률적인 언어 모델이라는 점이 다를 뿐입니다.

이 글에서는 LLM 앱을 실서비스로 운영하기 위해 컨테이너, 프롬프트 캐싱, 드리프트 모니터링 세 축을 어떻게 잡는지 정리해 봅니다.

## 왜 LLM에도 MLOps인가

전통적인 MLOps는 모델 학습과 배포를 자동화하는 개념이었습니다.

LLM 시대에도 이 아이디어는 살아있지만, 우리가 하는 일은 조금 다릅니다. 대부분의 서비스는 파운데이션 모델을 API로 호출하고, 그 위에 프롬프트와 도구를 얹어 에이전트를 만듭니다. 그래서 우리에게 필요한 MLOps는 학습 파이프라인이라기보다 프롬프트, 도구, 에이전트, 평가 데이터를 함께 버전 관리하고 관측하는 시스템에 가깝습니다.

바꿔 말하면, 배포 대상은 모델 가중치가 아니라 프롬프트와 오케스트레이션 코드입니다. 관측 대상은 GPU 활용률이 아니라 토큰 비용과 응답 품질입니다.

이 관점만 잡아도 이후 설계가 훨씬 단순해집니다.

## 컨테이너로 LLM 앱 패키징하기

가장 먼저 할 일은 LLM 앱을 컨테이너로 감싸는 것입니다.

에이전트 서비스라고 해도 결국은 HTTP API입니다. 요청이 오면 프롬프트를 만들고, 도구를 호출하고, 응답을 돌려주는 서버입니다. 우리가 이미 잘하는 일입니다.

```dockerfile
FROM node:22-alpine

WORKDIR /app

COPY package.json package-lock.json ./
RUN npm ci --omit=dev

COPY . .

ENV NODE_ENV=production
ENV PORT=8080

EXPOSE 8080

CMD ["node", "dist/server.js"]
```

특별할 게 없어 보이지만, 여기서 몇 가지 원칙을 지키면 운영이 훨씬 편해집니다.

첫째, 프롬프트 템플릿과 도구 정의를 이미지 안에 함께 넣습니다. 프롬프트를 런타임 환경변수로 주입하면 배포 이력과 프롬프트 변경 이력이 어긋납니다.

둘째, API 키 같은 자격 증명은 이미지 밖에서 주입합니다. 이건 일반 백엔드와 같습니다.

셋째, 모델 이름과 파라미터는 명시적으로 이미지에 태깅합니다. 같은 코드라도 `claude-opus-4-7`을 쓰던 이미지와 `claude-opus-4-8`을 쓰던 이미지는 완전히 다른 아티팩트입니다.

이렇게 해두면 문제가 터졌을 때 "어떤 이미지, 어떤 프롬프트, 어떤 모델이 그 응답을 만들었는가"를 한 줄로 답할 수 있습니다.

## 프롬프트 캐싱으로 비용 잡기

배포가 끝나면 다음으로 부딪히는 문제가 비용입니다.

LLM 청구서에서 가장 큰 비중을 차지하는 건 대개 반복되는 시스템 프롬프트, 도구 정의, 문서 컨텍스트입니다. 매 요청마다 같은 수천 토큰을 다시 인코딩하고 있는 겁니다.

주요 제공사들은 이걸 줄이기 위해 프롬프트 캐싱을 지원합니다. 개념은 단순합니다. 자주 재사용되는 접두어(prefix)를 캐시에 올려두고, 이후 요청에서는 그 부분을 훨씬 싼 값으로 읽어옵니다.

문제는 캐시 쓰기가 공짜가 아니라는 겁니다. 캐시 write는 일반 입력 토큰보다 조금 더 비싸고, 캐시 read는 훨씬 쌉니다. 그래서 breakeven 계산이 필요합니다.

간단하게 잡아보면 다음과 같습니다.

```text
- 입력 토큰 단가: 1
- 캐시 write 단가: 1.25 (입력의 1.25배)
- 캐시 read 단가: 0.1  (입력의 10%)

- 캐시 대상 프롬프트 크기: 5,000 토큰
- 캐시 없이 처리하는 비용: 5,000 * 1        = 5,000
- 캐시 첫 write 비용:        5,000 * 1.25     = 6,250
- 캐시 read 1회 비용:        5,000 * 0.1      = 500

- 캐시가 이득이 되는 재사용 횟수(n):
    6,250 + 500 * (n - 1) < 5,000 * n
    5,750 + 500n < 5,000n
    5,750 < 4,500n
    n > 1.28
```

즉, 같은 캐시가 두 번만 재사용돼도 이미 이득입니다. 실무에서 시스템 프롬프트는 수천 번 재사용되므로 사실상 무조건 켜는 것이 맞습니다. 위 단가 비율은 Anthropic 프롬프트 캐싱 기준 예시입니다. 제공자와 티어에 따라 다르니 절대값보다 손익분기를 잡는 방식만 기억해 두면 됩니다.

다만 캐시 히트를 실제로 얻으려면 프롬프트 앞부분이 바이트 단위로 동일해야 합니다. 사용자 이름이나 타임스탬프가 시스템 프롬프트 앞에 섞여 들어가면 매번 캐시 미스가 납니다. 저는 배포 후에 캐시 히트율을 지표로 뽑고, 미스가 많으면 프롬프트 구조부터 다시 봅니다.

## APM 위에 얹는 관측 계층

관측 이야기로 넘어가면 백엔드 개발자에게 좋은 소식이 있습니다.

우리가 이미 쓰고 있는 APM, 로깅, 메트릭 스택 위에 얇은 레이어만 얹으면 됩니다. Datadog이든 Grafana든 이미 있는 대시보드에 몇 가지 지표를 추가하는 형태입니다.

기본적으로 잡아야 할 지표는 다음과 같습니다.

- 요청당 입력 토큰 수, 출력 토큰 수
- 캐시 write 토큰, 캐시 read 토큰
- 요청당 예상 비용 (USD)
- 첫 토큰까지의 지연(TTFT)과 전체 응답 지연
- 모델별, 프롬프트 버전별 태그

이걸 span attribute나 metric label로 붙여두면 나중에 "지난주에 왜 갑자기 비용이 튀었나"를 30초 안에 답할 수 있습니다. 대개 원인은 프롬프트를 조금 늘렸는데 그게 캐시 경계를 깨뜨렸거나, 새 도구 정의가 매 요청마다 붙어 들어간 경우입니다.

로그는 조금 더 조심스럽게 다룹니다. 프롬프트와 응답 전체를 그대로 남기면 PII 문제가 생기기 쉽고, 스토리지 비용도 무시하지 못합니다. 저는 요청 ID로 샘플링해서 일부만 저장하고, 나머지는 해시와 토큰 수만 남깁니다.

## 드리프트와 품질 모니터링

비용과 지연이 잡히면 남는 건 품질입니다.

LLM은 결정적 시스템이 아니라서, 어제까지 잘 되던 케이스가 오늘 갑자기 이상해질 수 있습니다. 원인은 크게 세 가지입니다. 사용자 입력 분포가 바뀌었거나, 우리가 프롬프트를 손댔거나, 제공사가 모델을 조용히 업데이트했거나.

세 가지 모두 드리프트라고 부를 수 있습니다.

입력 분포 드리프트는 상대적으로 다루기 쉽습니다. 요청 임베딩을 주기적으로 샘플링해서 클러스터가 어디로 옮겨가는지 보면 됩니다. 새로운 종류의 질문이 늘어나고 있다면 프롬프트를 확장할 시점입니다.

응답 품질 드리프트는 더 까다롭습니다. 저는 두 가지를 병행합니다.

첫째, 골드 데이터셋을 두고 CI에서 매 배포마다 자동 평가를 돌립니다. 정답이 명확한 케이스는 정규식이나 스키마로, 애매한 케이스는 LLM-as-judge로 채점합니다. 배포 전에 스코어가 떨어지면 그 배포는 막습니다.

둘째, 프로덕션에서도 응답 샘플을 뽑아 별도 판정 파이프라인에 흘려보내고, LLM-as-judge 스코어의 이동평균을 대시보드에 띄웁니다. 이 평균이 임계치 밑으로 떨어지면 알림이 옵니다.

```text
- 배포 시점 t=0의 이동평균 스코어: 0.86
- t=7일: 0.84
- t=14일: 0.79   ← 알림 발동
- 원인 조사: 신규 도구 응답 포맷이 프롬프트 예시와 어긋남
```

이런 지표는 완벽하지 않습니다. LLM-as-judge 자체가 편향을 가지고 있고, 사용자 만족도와 완전히 일치하지도 않습니다. 그래도 아무 지표가 없는 것보다는 훨씬 낫습니다. 최소한 나쁜 배포가 슬금슬금 흘러가는 걸 며칠 안에 잡아낼 수 있습니다.

## 프로덕션 트레이드오프

마지막으로 지연, 처리량, 비용 사이의 균형을 언급해야 합니다.

같은 기능을 구현하는 방법은 여러 가지입니다. 더 큰 모델을 한 번 부르는 방법, 작은 모델을 여러 번 부르는 방법, 캐시를 크게 잡는 방법, 스트리밍으로 지연을 감추는 방법. 각각의 선택이 지연과 처리량, 비용을 다르게 만듭니다.

정답은 없지만 몇 가지 원칙은 있습니다.

사용자가 첫 글자를 기다리는 화면이라면 TTFT를 우선합니다. 스트리밍을 쓰고, 시스템 프롬프트를 짧게 유지하고, 캐시로 프리필을 줄입니다.

배치 처리라면 처리량과 비용을 우선합니다. 요청을 묶어 보내고, 큰 프롬프트를 캐시에 태우고, 필요하면 작은 모델로 라우팅합니다.

에이전트처럼 여러 번 호출하는 워크플로우라면 각 단계의 모델을 다르게 잡습니다. 라우팅과 요약은 작은 모델로, 실제 판단은 큰 모델로 나눕니다. 이 조합만 잘 잡아도 비용이 절반 이하로 떨어지는 경우가 많습니다.

여기에 하나 더 얹을 원칙은 출력 형식을 느슨하게 두지 않는 것입니다. 응답을 자유 텍스트로 받으면 파싱이 실패할 때마다 재시도가 붙고, 재시도는 곧 지연과 비용입니다. 구조화 출력(structured output)으로 JSON 스키마나 tool 형식을 강제하면 형식 오류로 인한 재시도가 줄고, 후처리 코드도 단순해집니다. 확률적 모델을 파이프라인에 끼워 넣을 때 형식만이라도 결정적으로 못 박아 두면 운영이 한결 안정적입니다.

## 마무리

LLM MLOps라는 말은 거창하지만, 실제로 하는 일은 우리가 이미 잘하는 것들입니다.

컨테이너로 아티팩트를 만들고, 캐시로 비용을 줄이고, 지표로 품질을 감시하고, 트레이드오프를 명시적으로 선택합니다. 다만 대상이 확률적이라는 사실 하나 때문에, 지표를 조금 더 촘촘하게 잡고 배포를 조금 더 조심스럽게 해야 할 뿐입니다.

LLM 기능을 실서비스에 올리는 팀에게 가장 큰 도움이 되는 건 화려한 신기술이 아니라, 우리가 원래 알던 배포·관측·회귀 방지 습관을 새 대상에 그대로 적용하는 것입니다.
