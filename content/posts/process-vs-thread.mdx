## 들어가며

백엔드를 하다 보면 "이 작업을 별도 프로세스로 띄울까, 스레드로 돌릴까"를 판단해야 하는 순간이 옵니다.

면접 단골 질문이라 개념만 외워두는 경우가 많은데, 사실 이건 실무 설계 결정입니다. 워커를 프로세스로 나눌지 스레드 풀로 갈지, 파이썬에서 왜 `multiprocessing`을 써야 하는지, 한 요청이 죽었을 때 다른 요청까지 같이 죽는지 같은 문제가 전부 여기서 갈립니다.

이 글은 프로세스와 스레드를 "격리와 공유의 트레이드오프"라는 하나의 축으로 정리합니다.

## 프로세스란

프로세스는 실행 중인 프로그램의 인스턴스입니다.

OS가 자원을 할당하는 기본 단위이고, 각 프로세스는 자기만의 독립된 주소 공간(가상 메모리)을 가집니다. 코드, 힙, 스택, 데이터 세그먼트가 모두 그 프로세스만의 것이고, 다른 프로세스의 메모리를 직접 들여다볼 수 없습니다. 커널은 각 프로세스를 PCB(Process Control Block)로 관리하며, 파일 디스크립터, 권한, 메모리 매핑 같은 정보를 여기에 담습니다.

핵심은 격리입니다. 한 프로세스가 잘못된 포인터로 메모리를 망가뜨려도 그 피해는 자기 주소 공간 안에 갇힙니다.

## 스레드란

스레드는 프로세스 안에서 실제로 코드를 실행하는 흐름입니다.

하나의 프로세스는 여러 스레드를 가질 수 있고, 같은 프로세스의 스레드들은 코드, 힙, 데이터, 열린 파일 디스크립터를 공유합니다. 대신 각 스레드는 자기만의 스택, 레지스터, 프로그램 카운터를 가집니다.

즉 스레드는 "같은 집에 사는 식구"입니다. 거실(힙)과 냉장고(전역 데이터)는 공유하지만, 각자 자기 책상(스택)에서 일합니다. 공유하기 때문에 서로 데이터를 주고받기가 쉽지만, 동시에 같은 데이터를 건드리면 충돌(race condition)이 납니다.

## 무엇이 다른가

| 기준 | 프로세스 | 스레드 |
|------|----------|--------|
| 메모리 | 독립된 주소 공간 | 프로세스 내에서 공유 |
| 생성 비용 | 무거움 | 가벼움 |
| 컨텍스트 스위치 | 비쌈 (주소 공간 전환) | 상대적으로 쌈 |
| 통신 | IPC 필요 | 공유 메모리로 즉시 |
| 장애 전파 | 격리됨 (하나 죽어도 생존) | 하나가 프로세스를 죽이면 전부 사망 |
| 동기화 | 대체로 불필요 | 락/뮤텍스 필요 |

## 격리와 공유, 그리고 통신 비용

가장 큰 차이는 메모리 격리이고, 통신 비용은 그 대가입니다.

프로세스는 격리되어 있어 안전합니다. 워커 하나가 세그폴트로 죽어도 나머지 워커는 멀쩡합니다. 대신 프로세스끼리 데이터를 주고받으려면 IPC(파이프, 소켓, 공유 메모리, 메시지 큐)를 거쳐야 하고, 이건 대체로 직렬화와 복사를 동반해서 비쌉니다.

스레드는 메모리를 공유하니 통신이 사실상 공짜입니다. 그냥 같은 변수를 읽고 쓰면 됩니다. 대신 두 스레드가 같은 변수를 동시에 수정하면 결과가 깨지므로, 락으로 순서를 강제해야 합니다. 그리고 락은 그 자체로 데드락, 경합, 성능 저하의 원천입니다.

컨텍스트 스위치 비용도 다릅니다. 프로세스를 전환하면 주소 공간이 통째로 바뀌면서 TLB를 비우는 등 캐시가 차가워집니다. 같은 프로세스 안의 스레드 전환은 주소 공간이 그대로라 이 비용이 작습니다.

## 실무에서 보이는 선택들

이 트레이드오프는 언어 런타임에서 특히 뚜렷하게 드러납니다.

```python
# CPython: GIL 때문에 스레드로는 CPU 병렬이 안 된다
# CPU 바운드 작업은 프로세스로 나눠야 한다
from multiprocessing import Pool

def heavy(n):
    return sum(i * i for i in range(n))

with Pool(4) as p:
    results = p.map(heavy, [10_000_000] * 4)  # 4코어를 실제로 쓴다
```

CPython에는 GIL(Global Interpreter Lock)이 있어서, 한 프로세스 안의 여러 스레드가 동시에 파이썬 바이트코드를 실행하지 못합니다. 그래서 CPU 바운드 작업은 스레드를 아무리 늘려도 빨라지지 않고, `multiprocessing`으로 프로세스를 나눠야 여러 코어를 씁니다. 반대로 I/O 바운드 작업은 GIL이 I/O 대기 중에 풀리기 때문에 스레드나 async로도 충분합니다.

## 언제 무엇을 쓰나

정리하면 판단 기준은 단순합니다.

- 장애 격리, 보안 경계, 안정성이 중요하면 프로세스로 나눕니다. 신뢰할 수 없는 코드를 실행하거나, 한 작업의 크래시가 전체를 무너뜨리면 안 될 때입니다.
- 데이터를 자주 공유하고 오버헤드를 낮춰야 하면 스레드를 씁니다.

## 마무리

프로세스는 격리이고 스레드는 공유입니다.

격리는 안전을 주지만 통신이 비싸고, 공유는 빠르지만 동기화라는 숙제를 남깁니다. 어느 쪽이 정답인지는 "이 작업들이 서로 얼마나 얽혀 있고, 하나가 죽었을 때 나머지가 어떻게 되어야 하는가"에 달려 있습니다.

요즘은 goroutine이나 async처럼 더 가벼운 동시성 추상화를 많이 쓰지만, 그 밑바탕에는 여전히 이 프로세스와 스레드가 깔려 있습니다. 추상화가 편해질수록, 밑에서 무엇이 격리되고 무엇이 공유되는지는 오히려 더 또렷하게 알고 있어야 합니다.
