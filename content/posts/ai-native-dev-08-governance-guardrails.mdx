## 들어가며

에이전트가 코드를 잘 쓴다는 얘기는 이제 뉴스도 아닙니다.

문제는 그 에이전트를 실제 프로덕션 시스템에 붙였을 때 벌어집니다. 프로덕션 DB에 접근할 수 있는 에이전트가 실수로 `DELETE FROM users` 를 실행하면 어떻게 될까요. IAM 토큰을 가진 에이전트가 잘못된 정책 파일을 밀어붙이면요. 배포 파이프라인을 조작할 수 있는 에이전트가 조작된 이미지를 배포하면요.

이 질문이 최근 몇 년 사이 조직 안에서 계속 반복되고 있습니다. 답은 대부분 같습니다. 에이전트의 권한을 명시적으로 좁히고, 경계를 넘으려는 순간을 코드로 감지하고, 감사 로그로 사후 검증할 수 있게 하자는 것입니다.

이 글에서는 bounded autonomy 라는 관점으로 에이전트 시스템의 가드레일을 어떻게 짤지, 그리고 백엔드 개발자가 오래 익혀 온 "롤백 마인드셋"을 어떻게 이식할지 정리해봅니다.

## bounded autonomy 라는 개념

bounded autonomy 는 말 그대로 "경계가 있는 자율성" 입니다.

에이전트에게 완전한 자율성을 주는 것도, 매번 사람이 승인해야 하는 것도 답이 아닙니다. 대신 사전에 정의한 범위 안에서는 에이전트가 스스로 행동하고, 그 범위를 넘는 순간에는 사람의 승인을 요구하도록 만드는 것입니다.

이 발상은 IAM에서 이미 익숙합니다. 어떤 서비스 계정은 특정 버킷의 읽기만 가능하고, 다른 계정은 특정 큐에 쓰기만 가능합니다. 에이전트도 같은 원칙으로 다뤄야 한다는 것입니다.

## DB write를 막는 IAM 패턴

가장 흔한 사례가 DB 접근 제어입니다.

코드 리뷰나 데이터 조회를 하는 에이전트에게 굳이 write 권한을 줄 이유가 없습니다. 그런데 편의를 위해 admin 계정을 그대로 넘겨주면 사고 확률이 급격히 올라갑니다.

```sql
-- 읽기 전용 에이전트 롤
CREATE ROLE agent_readonly;
GRANT CONNECT ON DATABASE app_prod TO agent_readonly;
GRANT USAGE ON SCHEMA public TO agent_readonly;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO agent_readonly;

-- 쓰기 가능한 에이전트 롤 (마이그레이션 전용)
CREATE ROLE agent_migrator;
GRANT CONNECT ON DATABASE app_prod TO agent_migrator;
GRANT USAGE ON SCHEMA public TO agent_migrator;
GRANT SELECT, INSERT, UPDATE ON specific_tables TO agent_migrator;
```

이렇게 롤을 분리하면 에이전트가 잘못된 쿼리를 시도해도 DB 레벨에서 거부됩니다. 애플리케이션 코드 위에서 "이거 하지 마" 라고 프롬프트로 부탁하는 것과는 신뢰도가 다릅니다.

같은 방식으로 파일 시스템, 네트워크, 배포 파이프라인, 클라우드 리소스도 최소 권한 원칙으로 좁혀야 합니다. 이 부분에 대한 감각은 백엔드 개발자가 늘 해오던 일이기 때문에 오히려 강점이 있습니다.

## 방어에도, 공격에도 쓸 수 있다는 사실

에이전트 코딩이 무서운 이유 하나는 같은 도구가 방어에도 공격에도 쓰인다는 점입니다.

취약점 스캐너를 자동화하는 것도 에이전트고, 스캔된 취약점을 활용해 실제 공격 코드를 짜는 것도 에이전트입니다. 배포 파이프라인을 감시하는 것도, 그 파이프라인을 조작해 백도어를 심는 것도 같은 종류의 에이전트로 가능해집니다.

이 사실은 두 가지를 의미합니다. 하나는 내부 에이전트의 권한을 좁혀야 한다는 것이고, 다른 하나는 외부 에이전트가 우리 시스템을 표적으로 삼는 시대가 이미 왔다는 것입니다.

방어 관점에서 해야 할 일은 명확합니다. 코드 리뷰에서 흔한 취약점 패턴을 자동으로 찾고, CI에서 의심스러운 커밋을 차단하고, 프로덕션 접근에 대해 세션 단위 감사 로그를 남깁니다.

## 스키마 검증과 드리프트 체크

에이전트가 만든 산출물을 그대로 신뢰하지 않으려면 검증 레일을 만들어야 합니다.

```yaml
# ci/schema-check.yml
rules:
  - name: schema-drift
    run: |
      pnpm prisma db pull --schema=schema.prisma
      git diff --exit-code schema.prisma
    fail_message: "prod DB와 schema.prisma가 어긋납니다"

  - name: forbidden-pattern
    run: rg "await db.query\(.*\+.*\)" src/
    on_match_fail: "raw SQL concat 금지, ORM 또는 parameterized query 사용"

  - name: agent-generated-tag
    run: rg "@ai-generated" src/ --files-with-matches
    then: require-human-review
```

핵심 아이디어는 에이전트가 만든 코드는 반드시 검증 파이프라인을 통과하도록 만드는 것입니다.

스키마 드리프트 체크는 특히 유용합니다. 에이전트가 마이그레이션을 만들고 나면 실제 DB와 코드상 스키마가 어긋날 수 있는데, CI에서 diff를 강제로 확인하지 않으면 이 어긋남을 오랫동안 발견하지 못합니다.

린트 규칙도 같은 원리입니다. "SQL injection 가능한 패턴 금지", "특정 API는 인증 미들웨어 필수", "특정 디렉터리는 사람만 수정 가능" 같은 규칙을 코드로 만들어두면 에이전트가 잘못된 방향으로 가는 순간 빌드가 실패합니다.

## 감사 로그 스키마

에이전트가 무엇을 언제 어떻게 했는지 기록하는 감사 로그는 사후 검증의 핵심입니다.

```sql
CREATE TABLE agent_audit_log (
    id BIGSERIAL PRIMARY KEY,
    session_id UUID NOT NULL,
    agent_name VARCHAR(100) NOT NULL,
    model_name VARCHAR(100) NOT NULL,
    action_type VARCHAR(50) NOT NULL,
    target_resource TEXT NOT NULL,
    input_hash VARCHAR(64) NOT NULL,
    output_hash VARCHAR(64) NOT NULL,
    risk_score INTEGER NOT NULL,
    human_approver VARCHAR(100),
    approved_at TIMESTAMP,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    INDEX idx_session (session_id),
    INDEX idx_risk (risk_score, created_at)
);
```

여기서 중요한 필드는 `input_hash` 와 `output_hash` 입니다. 문제가 생겼을 때 "그때 에이전트가 정확히 어떤 입력을 받아 어떤 출력을 냈는가" 를 재현 가능하게 만들기 위한 최소 정보입니다.

`risk_score` 필드도 놓치면 안 됩니다. 이 점수를 기준으로 자동 실행할지, 사람 승인을 요구할지가 갈립니다.

## 위험도 스코어링과 휴먼 오버사이트

모든 결정에 사람이 승인하도록 만들면 자동화의 이점이 사라집니다. 반대로 모두 자동 실행하면 사고가 납니다.

그래서 위험도 점수를 계산해 임계값 이상일 때만 사람을 부르는 방식이 필요합니다.

```text
risk_score = 0

# 대상 리소스
if target is production_db:      score += 40
if target is prod_config:        score += 30
if target is staging_env:        score += 10
if target is code_only:          score += 5

# 액션 종류
if action == "DELETE":           score += 30
if action == "SCHEMA_CHANGE":    score += 25
if action == "DEPLOY":           score += 20
if action == "READ":             score += 0

# 변경 규모
if lines_changed > 500:          score += 15
if files_changed > 20:           score += 10

# 시간대
if outside_business_hours:       score += 10

if score >= 50: require_human_approval()
if score >= 80: require_two_person_approval()
```

이 로직이 정확할 필요는 없습니다. 중요한 것은 "위험도라는 축을 명시적으로 정의했다" 는 사실 자체입니다. 팀 안에서 이걸 놓고 얘기할 수 있게 되면 논쟁이 훨씬 구체적이 됩니다.

## 롤백 준비 마인드셋 이식하기

백엔드 개발자에게 익숙한 습관 하나는 "이 변경을 되돌릴 수 있는가" 를 먼저 묻는 것입니다.

마이그레이션을 쓰면 다운 스크립트를 같이 쓰고, 배포는 카나리로 시작하고, 피처 플래그로 언제든 끌 수 있게 만들고, 에러가 감지되면 자동 롤백하는 알럿을 걸어둡니다. 이 습관을 에이전트 시스템에도 그대로 옮기면 됩니다.

에이전트가 만든 마이그레이션은 반드시 다운 마이그레이션을 요구합니다. 에이전트가 배포한 변경은 피처 플래그 뒤에 두거나 카나리로만 나갑니다. 에이전트가 만든 리팩터링은 짧은 관찰 기간을 두고 이상 징후가 있으면 자동 revert 합니다.

이렇게 두면 에이전트가 실수해도 사고의 폭발 반경이 좁아집니다. 신뢰는 "실수 안 할 것" 이라는 기대가 아니라 "실수해도 복구 가능한 시스템" 이라는 구조에서 옵니다.

## 사람의 개입 지점 설계

어디에 사람이 들어와야 하는지는 사고를 겪은 뒤에 배우는 경우가 많습니다. 미리 몇 가지 지점을 정해두면 좋습니다.

첫 번째는 배포 게이트입니다. 에이전트가 스테이징까지는 자동 배포할 수 있어도 프로덕션은 사람이 승인합니다.

두 번째는 스키마와 IAM 정책 변경입니다. 이 두 카테고리는 영향 범위가 넓고 복구가 어렵기 때문에 사람이 확인해야 합니다.

세 번째는 이상 감지 시점입니다. 감사 로그에서 에이전트의 행동 패턴이 갑자기 바뀌거나, 실패율이 급등하거나, 위험도 높은 액션이 몰릴 때 사람이 개입합니다.

이 지점들을 미리 정의해두면 "언제까지 지켜봐야 하지" 라는 애매한 상태에서 벗어날 수 있습니다.

## 마무리

에이전트에게 자율성을 주는 것과 통제를 유지하는 것은 대립 관계가 아닙니다.

경계를 명확히 그어두면 그 안에서는 오히려 더 과감하게 자율성을 줄 수 있습니다. IAM으로 권한을 좁히고, 스키마 검증으로 산출물을 걸러내고, 감사 로그로 사후 검증을 준비하고, 위험도 스코어링으로 사람 개입 지점을 자동화하면 됩니다.

이 모든 작업은 백엔드에서 오래 해왔던 일과 크게 다르지 않습니다. 최소 권한 원칙, 방어적 프로그래밍, 롤백 준비, 감사 가능성. 도구는 새롭지만 원칙은 익숙합니다.

앞으로 에이전트가 프로덕션에 더 깊이 들어갈수록, 좋은 에이전트를 만드는 능력만큼이나 좋은 가드레일을 만드는 능력이 팀의 성패를 가르게 될 것 같습니다.
